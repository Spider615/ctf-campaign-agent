# Skill 问答实施前实测

日期：2026-10-25（北京时间）。本次只运行独立实验，不修改产品运行器、活动创建或正式 Skill。记录的是当前本机与网关条件下的结果，不是新方案的完整业务验收。

## 1. 环境和证据

- Node.js 22.23.1；安装的 Agent SDK 0.3.272，实际启动的运行时 2.1.272。
- 使用 `.dev.vars` 指定的公司模型网关与原模型配置，经项目原有 `createModelGateway` 转换。未切换供应商、未更新依赖、未重启正在服务的应用。
- SDK 实验使用合成数据、独立 MCP、空的内置工具列表、`settingSources: []`、`persistSession: false`，未传 maxTurns。没有加载用户个人配置或业务客户数据。
- 合成协议实验设 `effort=low`、关闭 thinking；用于测轮数、调度、压缩和取消机制。其模型耗时不能直接当作真实营销推理的耗时预测或效果验收。
- 原始脚本、逐事件 JSONL、摘要 JSON 位于仓库外：`~/Library/Application Support/ctf-campaign-agent/preflight-20261025/`。其中 sdk-preflight.mjs、sdk-compaction-once-preflight.mjs、mysql-preflight.mjs、provider-preflight.mjs、mysql-cancel-preflight.mjs 可复跑；凭据从现有环境读取，不写入记录。
- 单次实验设 8 分钟 watchdog，只用于避免实验挂死，全部实验均未触及；不是建议给产品增加总时限。
- `evidence-manifest.json` 保存本次 33 份脚本/记录的文件名、字节数和 SHA-256，便于核对原始证据；不包含凭据或运行时目录文件。

## 2. SDK 轮数：可以去掉旧 12 轮上限

实验：真实模型逐次取得不可预知的下一张票据，必须完成 16 次顺序工具调用，最后返回 LOOP16_OK；票据由工具当场生成，不能靠模型提前推算。

结果：16 次工具调用全部完成；SDK num_turns=17；实际网关请求 17 次；总耗时 41.313 秒；success。当前进程未传 --max-turns，也未设置环境 max turns。

这证明当前安装组合能越过旧上限，并不把 16 次等同于数学意义的“无限实测”。SDK JS 仅在显式传 maxTurns 时添加 CLI 参数；[官方 CLI 参考](https://code.claude.com/docs/en/cli-reference#cli-flags)也明确 max-turns 默认不设上限。实施可按用户要求省略上限，无需另设一个很大的数。

## 3. SDK 并发：只读标记有效

同一真实模型回复请求两个互相独立的工具，每个固定等待 4 秒。工具的等待用于测调度，不代表 SQL 速度。

| 配置 | A、B 从首个开始到最后完成 | 全会话耗时 | 结果 |
|---|---:|---:|---|
| 不声明只读 annotations | 8.015 秒 | 12.386 秒 | 串行，合计正确 |
| 声明 readOnlyHint=true | 4.144 秒 | 8.523 秒 | 两次调用重叠，合计正确 |
| 声明只读，且逐次走 canUseTool | 4.146 秒 | 12.596 秒 | 两次权限回调均真实执行，并发成立 |

第三项总时长受本次上游响应波动影响，不能用全会话时间判断是否并发；调用起止区间证明了调度行为。模型是否提出并发调用仍由模型决定，不把每题并发写成业务流程。

另有重要发现：裸 allowedTools 工具名会提前自动批准，SDK 发出 CLAUDE_SDK_CAN_USE_TOOL_SHADOWED，canUseTool 不会再检查该工具。实测改为空 allowedTools 并由精确白名单 canUseTool 决定后，回调和只读并发都正常。新运行器的权限实现不能同时声称“裸名自动批准”与“每次都经过回调”。参考[官方权限顺序](https://code.claude.com/docs/en/agent-sdk/permissions)。

## 4. 长上下文：自动压缩可用，但大返回值会先丢失可见性

### 分页实验

- 连续读取 8 页合成数据，每页约 13,839 字符；单次工具结果的尾部行确实进入真实网关请求。
- 仅为尽快触发测试，在独立 SDK 子进程使用官方支持的 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=15`。未改产品配置；这不是建议生产也用 15%。
- 观察到两次真实 compact_boundary，trigger=auto：第一次 pre_tokens=32684、post_tokens=4270；第二次 pre_tokens=33648、post_tokens=4290。
- 压缩后继续读到第 8 页，最终返回 CORAL-734。这个标记在原提示及每一页都重复，所以本例只能证明压缩后继续执行与分页内容确实进入请求，不能单独证明早期唯一事实被保留。8 次业务工具调用对应 11 次真实模型请求，其中多出的请求含压缩；总耗时 40.263 秒。

### 只出现一次的随机事实补测

复查实验设计后另建 sdk-compaction-once-preflight.mjs，不覆盖旧记录：随机生成 PROJECT_CODE，仅第一页工具结果提供；原提示和后七页均不含其值，最终必须准确返回。工具拒绝跳页并记录纠错次数。

- 实际按顺序读完 8 页，跳页/重读纠错 0 次；仍观察到两次 trigger=auto 的 compact_boundary。
- 两次 pre/post token 数为 32876→4353、33874→4447；压缩后的实际网关请求仍包含被记住的随机值。
- 最终返回与随机期望值精确相等；11 次真实模型请求，总耗时 42.296 秒，success。业务工具全部逐次经过 canUseTool；只读权限名单未被 allowedTools 自动批准绕过。

结论：当前 SDK 与公司网关的自动压缩链路可以工作，且本例在两次压缩后保留了早期唯一事实。该合成实验不保证任意长业务任务的全部细节保留。完整事实仍应留在结果仓库，模型可按 resultId 重新分页读取。参考[官方上下文说明](https://code.claude.com/docs/en/agent-sdk/agent-loop#automatic-compaction)和[阈值变量说明](https://code.claude.com/docs/en/env-vars)。

### 大结果反例

另一个实验每页返回约 142,889 字符。虽然 SDK 最后返回 success，实际网关收到的每个工具结果仅约 1,636 字符，带文件提示且不含末尾测试行。这不是“模型看完全部数据”的成功证据。

[官方 MCP 文档](https://code.claude.com/docs/en/mcp#output-limits-and-warnings)说明：默认超过 50,000 字符的成功文本结果会转存文件，并有默认 token 限制。我们的目标运行器不开放文件读取，所以不能依赖自动转存后再让模型看文件。分页必须同时控制组数和序列化长度，且用尾部行/事实完整性测试验证数据实际进入请求，不能只测试工具返回对象。

## 5. 取消：需要应用侧中断等待并拒收迟到成功

| 实验 | 从发出 abort 到消费循环结束 | 观察 |
|---|---:|---|
| 只给 SDK AbortController，模型请求进行中 | 716 ms | 先收到迟到 success，随后才抛 aborted |
| 应用侧 next() 与取消竞速，模型请求进行中 | 8 ms | 立即结束，没有接收最终答案 |
| 只给 SDK AbortController，工具挂起 | 2009 ms | 工具退出后仍观察到一次后续模型请求 |
| 应用侧竞速，工具挂起 | 3 ms | 本地停止且没有接收最终答案 |

应用侧原型按计划采用取消竞速，并在读取下一条之后再次检查 signal。真实数据库会话也完成取消测试：在聚合 SQL 执行 200 ms 后中断，约 204 ms 从调用开始返回 AbortError，abort 到拒绝小于 1 ms；会话失效且原连接不再出现在 PROCESSLIST。它是组件实验，不代替页面完整链路测试。

上述 SDK 时间是本地消费循环退出，不代表云端运算或计费在几毫秒内停止。正式实现仍要连通浏览器、Workers、MCP 和数据库取消，并拒收 abort 后的结果；本次未宣称已完成 UI 端到端取消验收。

## 6. 真实 MySQL 并发：有收益，但小于原估计

环境：本机 Docker 的 MySQL 8.0.46（8.0 镜像）；Docker 分配 10 CPU、约 7.75 GiB 内存，容器没有额外 CPU/内存硬限额。使用配置中的只读账号，四条连接均显式设为只读事务。

负载：同一授权表、同一数据范围，按大区、优惠、日期、货类各执行一次聚合，含实收、毛利、订单。SQL 由现有 buildAnalysisAggregateQuery 生成。四条查询结果全部与串行基准的完整排序哈希一致。

先预热一次，再以不同顺序测试 1/2/4 并发各三次；没有清空 MySQL buffer pool，因此这是暖数据读取实验，不称为冷启动。

| 并发数 | 三次整组耗时（秒） | 中位数（秒） | 相对串行减少 |
|---|---|---:|---:|
| 1 | 18.833 / 19.032 / 20.278 | 19.032 | — |
| 2 | 17.626 / 16.465 / 16.073 | 16.465 | 13.5% |
| 4 | 13.958 / 12.951 / 13.158 | 13.158 | 30.9% |

该负载下四路并发约 1.45 倍，不能支持之前“60 秒查库一定降到 15–20 秒”的推测。并发下单条查询也变慢，说明资源竞争会吞掉部分收益。它仍是可用优化，但最终几十秒的目标还依赖减少无价值模型步骤、复用结果和真实问题回归。

## 7. 数据版本：目前不能开启可靠跨会话缓存

- 实测两次打开原分析 provider，打开耗时分别 911 ms、462 ms；datasetVersion 不同，且没有稳定 dataKey。随机版本只适合标识会话，不能用作持久缓存版本。
- 本次查询前后行数和日期范围未变化、聚合结果一致，只证明实验窗口内观察一致，不证明数据长期不可变。
- 当前账号 SHOW GRANTS 未显示写权限，但 MySQL server_read_only=0，其他账号仍可能更新。
- 容器导入脚本会核验 SQL 压缩包 SHA-256，但完成后清除下载目录，`.ctf-imported` / `.ctf-wide` 只写时间；当前本地数据卷也未发现这两份完成标记，不能把另一种部署的标记机制当成本机现状。

实施决定：现在不要拿“库表、行数、日期”当内容版本开启持久缓存，也不要据此宣称多连接共享快照。先沿用一致性读取；实施时需要建立可靠源修订及不可变读取约束，或者保持单连接与会话内缓存。原始数据摘要、源哈希和物化/语义编译版本的关系需要可核对，不能单加一个随意环境字符串便宣称一致。

## 8. 对实施计划的实际影响

1. 不设 maxTurns 有安装代码、官方说明和超过旧上限的实测支持。
2. 新只读查询工具应声明只读 annotations；若用 canUseTool 逐次判定，则不要被裸 allowedTools 提前批准绕过。
3. 取消竞速和 abort 后拒收不可省；SDK 单独 abort 并不足以保证产品马上停止显示。
4. 分页同时约束结果组数与返回长度，防止数据被 SDK 换成模型无权读取的文件引用。
5. 保留 SDK 自动压缩；不要为了“快”在产品强行设置本次实验用的 15% 阈值。
6. 四路 SQL 并发仅在一致性前提满足时启用，收益采用实测，不承诺线性提速。
7. 当前稳定数据版本尚缺，持久缓存的前置条件没有通过，不能把任务 2 整体标完成。
8. 新 Skill 尚未实现，真实业务 15 题、回答数字、最终 UI 和附件外层预算不在本次实验通过范围内。
