# Skill 驱动智能问答方案复审

日期：2026-10-25。以下原审查为实施前快照，范围是设计文档、实施计划与当时代码的对照；当时未实施产品功能。后续实施结论见文末及验收记录。

结论：原文档存在实质冲突和缺口，不能直接按“设计已完整”开始集成。已修正可以由代码证据确定的问题，并完成独立 SDK/MySQL 实验与营销原始来源核实；集成和业务验收仍在实施计划中。这里的“已修正”仅指文档，不能当作功能已实现或真实业务质量已验收。

## 主要发现

| 编号 | 级别 | 原问题与影响 | 当前代码证据 | 文档处理 |
|---|---|---|---|---|
| R1 | P1 | 用行数与日期作数据版本，等行数更新会命中过期缓存；计划与设计的版本规则还不一致 | `agent/analytics-operation-database.ts` 的 dimensionValueCache/cacheKey | 两份文档统一为可靠修订；升级目录与查询缓存；无法证明版本时不跨会话复用 |
| R2 | P1 | 四条独立连接不拥有同一物理快照，仅标同一 snapshotId 不能保证一致性 | MySQL provider 的显式事务和 session 身份 | 并发前验证不可变源/可靠修订，否则单连接；新池按数据源进程级共享，取消按逻辑会话隔离 |
| R3 | P1 | refs 为空且没有图时，页面没有数据出处入口；只保留图表事实还会删光普通查数的依据 | `app/components/analytics/plan-answer.tsx` 的 SourcePanel 与 PlanAnswerV4View；附件 recordDatabase 也遍历 evidence.facts | 保留实际已读事实和父链；新增“本次查数结果”入口，不冒充逐句核验 |
| R4 | P1 | 复用身份清洗函数会重新插入固定自我介绍，违反不要固定回复 | `app/lib/agent/reply-stream.ts` 的 withoutUnderlyingModel/SELF_INTRO | 新问答仅复用识别规则，清洗空稿由当前 Agent 改写；不动活动原清洗 |
| R5 | P1 | 附件外层仍有 240 秒预算、三次历史调用上限、固定复核，换内层运行器无法兑现全链路放开 | `agent/attachments/run-turn.ts` 的 ANSWER_BUDGET、wrapUpAt、analyze_attachment_history | 明确范围未定，默认保留附件注入；不能宣称附件也已无上限 |
| R6 | P1 | SDK 失败或中断前的一句“我去查”可能被当成后备最终正文，导致失败显示为完成 | 旧运行器原本检查 SDK result subtype；新计划只要求最后一段文本 | 仅 SDK success 且最终文本完整时后备；取消、错误、截断、异常 EOF 不冒充成功 |
| R7 | P2 | 只返回前 100 组且不支持续读，会限制模型取证；能力目录五个示例也不能覆盖所有活动 | `plan/prompt.ts` 的 MAX_LISTED_VALUES；原计划截断规则 | analyze 支持结果分页，inspect 支持维度取值分页，工具总数仍为五个 |
| R8 | P2 | 目录分页仅改格式化无效：MySQL 超过 600 个值不保存 values，门店/SKU 不在预读名单 | `agent/analytics-operation-database.ts` 的 MAX_DIMENSION_VALUES/预读维度；AnalysisDataSession 原无取值方法 | 明确新增底层受控 dimensionValues，覆盖 601+ 值、门店/SKU 与授权范围测试 |
| R9 | P2 | 并发登记会发生视图冲突；简单串行后，重复缓存结果又可能反复全量校验，抵消提速 | EvidenceRegistry.ingestAsync 的视图比较、合并冻结；operations.reuseResult | 串行登记、首发 session 单例、可信封存身份去重；翻页不重登记 |
| R10 | P2 | 无版本头入口仍启用旧固定回复，只有 v4 放开不等于所有新问答都放开 | `agent/http-handler.ts` 的 runner 选择；旧 analytics-run-turn | 明确 v3/v4 新请求走新运行器，无头新请求提示升级；旧消息读取与旧模型运行分开 |
| R11 | P2 | 放宽单条 v4 结构不能保证对话能保存：传输允许大结果，保存接口只有 2 MiB | `app/lib/analytics/stream.ts`；`app/lib/server/analytics-access.ts` 与 conversations PUT | 补保存、刷新、复制、追问闭环与 UTF-8 容量测试；不能静默丢失或虚报保存成功 |
| R12 | P2 | 时间线缺少失败总状态；新问答还会显示“正在核验”，与取消固定核验不符 | `chat/tool-timeline.tsx`、`analytics/history-message.tsx` | 增加真实总状态和适用标题；新问答整理文案与附件实际核验区分 |
| R13 | P2 | 一次 SDK query 被误解为一次模型 API 请求，会高估提速 | SDK query 中实际多轮请求；本地 model-gateway | 拆分启动次数、真实 API 次数、排队/SQL/缓存耗时；真实 SDK 验证并发和默认轮数 |
| R14 | P2 | 营销理论的原始出处尚未核实，“有字段”不等于现工具能做，例如分位数不等于阈值直方图 | AnalysisOrderDistribution 只有 p50/p90/p99；语义层有限动作 | 补命题到原始来源、限制和实际能力的逐条映射，不把方法参考当已实现能力 |
| R15 | P2 | 任务依赖、类型检查入口、洞察输入回归和维护文档同步不完整 | 任务 6 依赖两份 Skill；agent tsconfig 精确列入口；focusContext 在 context；AGENTS/CLAUDE 并存 | 补 5→6、8→9，evaluation 类型入口、洞察输入和活动夹具回放，更新两份说明 |

## 前置实测后的状态

实测记录见 [SDK 与数据库实验](../notes/2026-10-25-skill-qa-preflight.md)，来源与适用边界见 [营销研究索引](../../research/2026-10-25-marketing-theory.md)。原始脚本、日志与摘要留在仓库外，产品代码未修改。

- **R13 已补独立证据：** 真实 SDK 完成 16 次顺序工具调用；只读标记使两次工具执行重叠；自动压缩可继续运行；取消竞速可避免接收迟到成功。这些不代替新运行器集成验收。
- **R1/R2 的检查完成，但启用条件未通过：** 当前 provider 的版本仍随机、未取得可靠源修订；多连接并发的结果一致不能证明共享同一物理快照。跨会话缓存及多连接生产模式保持未启用。
- **并发收益已改用实测：** 四条真实 SQL 暖缓存串行中位数 19.032 秒，四路并发 13.158 秒，减少约 30.9%；不能采用“四倍提速”假设。
- **R7 新增实际风险：** 超大工具结果会转成模型无权读取的文件提示。计划增加字符预算和可续读分页；SDK success 不代表模型读过全部结果。
- **R14 已补来源核实：** 十个方向均有分级记录，正文、摘要、书目分开；现有方法未实现的净增识别、门槛直方图和客户价值没有被包装成已实现能力。收入持平与利润持平的公式及口径已分开。最终 Skill 条目与来源的逐项映射仍待 Skill 编写后验收。

## 仍不能下结论的事项

- **完整 SDK 业务链路：** 有限实验越过旧轮数上限，且安装代码与官方文档支持省略上限；这不是无限任务的数学证明。长业务语义保留、真实 analyze 并发、Skill 目录过滤以及页面到数据库取消仍需集成实测。
- **数据库版本：** 本次核查未取得可靠不可变修订，源账号无写权限也不证明其他账号不会更新。不能用旧的“行数/日期”键替代缺失证据。
- **附件范围：** 是否一起移除附件外层预算、固定复核和数字核验，需要明确。数据库智能问答可独立实施和验收，不等待附件范围才能推进。
- **大答案持久化：** 保留现存储容量时，必须明确显示保存失败并保留当前可见答案；若要保证更大结果长期保存，需要另补存储合同。
