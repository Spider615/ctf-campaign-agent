# 周大福营销活动生成 Agent 设计

> **已被取代**：本文的营销方案层、拆单和开单规则已不再使用，现行设计见 `2026-09-16-ics1811-sop-agent-design.md`，本文仅供追溯。

## 0. 硬约束（先写死，后面所有设计都受它约束）

1. **拿不到 `add_Discount.xls` 汇入模板原件，也拿不到生产码表。** 因此不生成可直接汇入的 Excel，主交付路径走 ICS 1811 逐字段填写清单。
2. **不登录、不调用、不提交周大福任何生产系统。** 即使生成了可录入的数据，实际系统操作也必须由运营人员在真实界面上完成。
3. **所有枚举值来自 PPT 截图，最新的一代是 2025 年，最老的是 2019 年，而现在是 2026 年。** 任何"当前系统就是这样"的表述都没有证据。每个枚举值必须带证据年份。
4. **不得编造任何内部代码表。** 未见底、有多版本冲突、或名称与落库码无映射的字段，只输出业务意图，由运营在界面上选。

## 1. 目标与验收标准

给周大福运营人员日常使用、并用于管理层演示的对话式营销活动生成 agent。用户用自然语言描述活动，agent 产出两层交付物：上层是营销活动方案，下层是 N 条 ICS 优惠开单草稿。生成后支持自然语言修改和手工修改，全部对话与版本记录持久化。

验收标准全部可机器判定，不含"生成得好"这类不可验收目标：

1. 任意一次生成的开单草稿 100% 通过第 7.1 节的 17 条校验。
2. 标记为 `ai` 来源的字段中出现任何内部代码表字段 = 失败。
3. 一句自然语言修改产生的 patch 只改动应改动的字段，diff 可见且可回滚。
4. 关闭浏览器重开，对话记录与版本链完整恢复。
5. 第二次为同一门店建活动时，让扣点与回款率自动预填，不再追问。
6. 顾客动作 = "只看到" 时，优惠区块整体关闭，输出"本次不建 ICS 单"的判定与理由。
7. 每个非空枚举值都能显示其证据年份与来源截图编号。
8. 表单填完后，"拆成 N 条 ICS 单"这个数字可由表单输入确定性算出，不是模型猜的。

## 2. 用户与场景

**运营人员（日常）**：每天建 2-5 个活动，其中多数是重复的门店促销。他要的是第 N 次比第 1 次便宜。

**管理层（演示）**：看一句话到完整方案的落差。

这两个目标在同一个首屏上互相冲突，因此分设入口、汇聚到同一个草稿状态机，不用一套 UI 硬凑。

## 3. 领域模型

### 3.1 活动类型是两个正交轴，不是一个标签

单标签分类会在边界案例上失效："七夕 × 联名款 × 满减"这个活动，选任何一个标签都会丢掉另外两块问题集。两个轴的证据来源也根本不同：

**轴 A · 由头（为什么是现在）**——可以从 25 条历史活动学。决定叙事、渠道默认值、效果口径、档期约束。

| 由头 | 历史条数 |
|---|---|
| 日历节点 | 7 |
| 品牌节点 / 自有系列首发 | 6 |
| 外部节点 / IP 窗口 | 5 |
| 线下场 | 4 |
| 门店日常经营 | 2 |
| 私域日常运营 | 1 |

由头是**事实陈述**而不是分类判断——运营接到任务时就知道这次是因为七夕、还是因为新系列上市。因此它可以直接问。

**轴 B · 让利机制（我方拿什么换）**——只能从 PPT 字段学，历史学不了。决定 `offer_type`、规则行结构、是否建单。

无让利 / 以旧换新换购 / 门槛型（满减·满折·满件折·每满减·每满返·联单）/ 直接价格（售价固定折扣·金价每克减免·每整克减免·分克重段·黄金工费打折）/ 赠品兑换 / 券核销

25 条历史活动中 `transaction_offer` 非空的只有 3 条。这批数据能教"活动长什么样、问什么问题、拆几条单"，教不了"折扣填多少"。压成一个标签等于用不可学的一半污染可学的一半。

**两个修饰符**（agent 推导，不是表单轴）：

- **是否涉及外部授权方** → 触发授权范围 / 期限 / 权益分配的问题块。这一条解决了联名的归类问题：周大福×百雀羚七夕礼盒的由头是七夕，联名是货品属性。
- **货品锁定方式** → OUTLET 活动与指定牌仔在这里落地，不用单列活动类型。

### 3.2 一个方案对应 N 条 ICS 单，从来不是一对一

拆单维度固定为 `批次/节点 × 市场 × 线上线下 × 门店范围层级 × 优惠机制`。表单必须采集全部五维，否则"拆成 N 条单"这个结论在数学上不可计算。

ICS 只覆盖成交规则。展览报名、VIP 邀约、扫码互动归 CRM/活动系统，券的面额与发放归发券系统。每个方案交付两份清单。

### 3.3 字段来源与证据年份

每个字段值携带两个元数据：

**来源 `provenance`**
- `user` — 运营明确提供
- `ai` — 模型生成，**只允许文案类**（对外传播名、ICS 开单名、活动内容、主张、话术）
- `default` — PPT 有明文默认值（周期 0、预告 0 天、货品范围 0、转换餐牌 0）
- `pending` — 必须由运营在真实界面上选的内部代码表

硬规则：`ai` 档永远不允许出现内部代码表字段，违反即校验失败。

**证据年份 `vintage`** — 该枚举值来自哪一年的截图，以及来源图片编号。agent 引用时必须明说："按 2021 年截图，如与现行不符请在界面上改。"

### 3.4 码表的两类处理

**可用**（截图已见底、编号连续、无版本冲突）：审批流 8 项、货品范围 0–6、转换餐牌 0/1、活动分组 3 项、线上线下 1/2、优惠性质 0/1、优惠类型 15 个中文名（无编号映射）。

**不可用**（未见底 / 多版本互斥 / 名称与落库码无映射）：会员级别（2021 版与 2024-25 版互斥）、售价类型（7 个中文名对 26 个单字符码，全篇无映射）、货类（未见底）、货类明细（随货类联动的二级字典）、品牌（从审批流反推，PPT 无品牌下拉展开图）、支付方式（未见底）、区域/分区/小区/城市/分行（未见底且有多版本）。

对不可用码表，产品输出业务意图而非具体值。例：不写"会员级别 = 黄金会员"，写"限会员：是，范围=中高等级及以上（请在界面勾选；截图存在两套互斥版本，以生产为准）"。

## 4. 交互设计

### 4.1 四个入口

首屏不是表单，是"从哪开始"：**新建 / 复制上次 / 从被拒的改 / 从示例**。

"从被拒的改"是必需的，不是锦上添花：1811 新建后不可原地改，1815 只能改活动名称、活动分组、日期、付款方式、优惠类型、折上折、线上/线下，且 PPT 明写"在审批拒绝之后才可以进行修改"。两条路的可改字段集与审批回路完全不同。

"从示例"是每个由头一份预置只读草稿，用作演示种子数据。不做模板管理 CRUD。

管理层演示走"新建"，运营日常走活动列表（复制 / 改）。两者汇聚到同一个草稿状态机。

### 4.1.1 表单不是入口，是 agent 对你那句话的理解回读

"新建"之后出现的第一个东西是空白对话框，不是表单。运营打一句话——"下个月华东区做个母亲节满减"——agent 用这句话**预填表单**，填上的字段标明来源，没填的高亮。

这一条同时解决两件事：日常场景下运营只需补高亮项而不是从零填 24 个字段；演示场景下管理层看到的是"打一句话，表单自己长出来"，而不是"AI 让人填表"。表单从拦路关卡变成理解的可视化。

表单与对话双向绑定：改表单即产生一条 `human` patch，对话里说一句也产生一条 `ai` patch，两者在同一条版本链上。

### 4.2 生成前表单

判据只有一条：**这个字段填错了，生成结果会不会整个作废？** 会则进表单，不会则扔进对话追问。

三类字段一律不进表单：PPT 有明文默认值的、可由已填字段硬规则派生的（活动分组、开单名、标语、审批流）、以及第 3.4 节列出的不可用码表。

**活动类型不进表单。** 它是内部归纳词汇，判据是"驱动力是价格机制还是节点情感"这种分类学口径。让运营做分类会错，而分类恰恰是 agent 该做的事。类型由 A 区四个意图字段推导，agent 在首句回读里给出判定与判据，运营只做确认或推翻。

**客群年龄区间与性别不设字段。** 25 条历史中给出精确年龄区间的是 0 条，数据明确警告"不应自动填成年轻人"。这个框一旦存在，运营会随手填"25-35 岁女性"，编造的数字会一路长进方案、投放建议和效果预估。这是演示压力下最容易被加回来的字段，写成硬规则守住。

| 区 | 字段 | 控件 | 必填 | 说明 |
|---|---|---|---|---|
| A | 由头类型 | 单选 6 项 + 自由输入 | ✓ | 事实陈述而非分类判断 |
| A | 真实由头一句话 | 单行文本 | | 选填并给占位示例；必填会被敷衍 |
| A | 顾客做到哪一步才算数 | 单选：只看到/参与互动/到场/留资/下单/带旧货来换/**还没定** | ✓ | 决定 `ics_entry`，替代"是否含成交优惠"这个系统黑话 |
| B | 打的是哪类人 | 多选，按场合·关系·身份 | ✓ | 不按年龄 |
| B | 限不限会员 | 不限 / 限（范围描述）/ 还没定 | ✓ | 不选具体等级 |
| C | 业务大类 | 多选：镶嵌类·素金类·黄金类·赠品 + 其他（说明） | ✓ | 只用 PPT 正文确定值，不自行增补 |
| C | 主推系列 / 专款 | 自由文本 | | |
| C | 要收窄货品范围吗 | 二值开关 | | 展开后给完整 0–6 码表 + 指定系列 / 指定货号 |
| D | 让利机制 | 单选 6 项 + 还没定 | ✓ | |
| D | **档位表** | **行级表格，列随让利机制渲染** | 条件 | 一档一行；表头常驻"打几折填折扣率（8折→0.8），减多少钱填减免额（元/克）" |
| D | 让利由谁承担 | 公司全担 / 平台分担 / 合作方分担 + 比例 | | 不问会导致让利重复计算 |
| D | 能否与其他折扣、券叠加 | 是 / 否 / 还没定 | ✓ | → `discount_stacking` + `coupon_allowed` |
| E | 范围层级 | 单选：全国/区域/分区/指定门店/电商平台 | ✓ | |
| E | 范围编码 | **按层级动态渲染** | ✓ | 指定门店时出「行号 + 行名」两列表格；结构上保证三者不可能同时有值 |
| E | 覆盖市场 | 多选 | ✓ | |
| E | 渠道 | 多选 | ✓ | 勾选时实时显示"这会拆成 N 条 ICS 单" |
| F | **批次表** | **行级，每行独立起止** | ✓ | 结束日不可跳过 |
| F | 节点当年公历日期 | 日期 | 条件 | 农历节日必填，agent 不得自行推算 |
| F | 周内循环日 | 默认 0 | ✓ | 常驻，不靠对话关键词命中触发 |
| F | 长期活动子档期切法 | 按季度/按批次/按赛程/手动 | 条件 | 结束日为空或跨度超一年时强制 |
| G | 衡量指标 | 单选，选项按由头自动过滤 | | 禁止"预计销售额提升 X%" |
| G | 目标值 | 数字 | | 留空则 agent 不编 |
| H | 品牌线 | 下拉，标注"观测值，非完整枚举" | ✓ | 自动推导审批流并提示确认 |
| H | 让扣点 | 数字，按门店×业务大类预填 | ✓ | 必须显式回答；0 是合法值，与未答不可区分 |
| H | 回款率 | 同上 | ✓ | 超过 1 只做黄色提醒，不硬拦（实测回显过 1.1） |
| H | 支付方式有限制吗 | 二值开关 | ✓ | 一个二值问题挡掉 24 个复选框 |

H 区标题直写"AI 推不出来、只有你知道的几个数"，并注明"按上次该门店的值预填"。演示前需准备门店种子数据，避免台上出现两个空输入框。

长枚举一律用二值前置开关挡住：先问"要不要限制"，选"要"才展开清单。同样适用于会员级别、售价类型、限定排除项。

### 4.3 对话修改走 patch，不重新生成

全量重生成每次都漂移——改折扣会顺手换掉活动名，而且无法 diff。

LLM 只输出字段级 patch：`{op, path, value, reason, provenance}`。确定性代码 apply → validate。校验失败则把错误回喂模型再改一轮，最多 2 轮，仍失败则把冲突呈现给用户。

手工修改走**同一条 patch 通道**，只是 `source` 标为 `human`。因此历史记录格式统一，diff 与回滚逻辑只有一套。

### 4.4 交付物

提交表单后 agent 的第一句话不寒暄、不复述，直接给三个数字和一个缺口：

> 按你填的，这个方案要拆成 N 条 ICS 单（X 个批次 × Y 个市场 × 线上线下各一）。其中 A 条字段已齐，B 条卡住，卡在这两处：① … ② …。先解哪个？

当顾客动作 = "只看到"时，优惠区块整体消失，直接输出"本次不建 ICS 单"的判定与理由。这是演示里最建立可信度的一屏。

## 5. 数据模型

对话记录和生成记录是同一件事的两面，不建两套存储。

```
session(id, title, entry_mode, status, created_at, updated_at)
message(id, session_id, role, content, created_at, produced_version_id)
draft_version(id, session_id, seq, brief_json, ics_orders_json, created_by, patch_id, created_at)
patch(id, session_id, from_version, ops_json, source /* ai | human */, reason, model, tokens, created_at)
store_constant(store_code, business_category, concession_rate, collection_rate, updated_at)
codetable(field_key, value, label, vintage_year, source_image, completeness /* complete | truncated | conflicted */)
```

`draft_version` 是不可变快照。`store_constant` 是唯一让产品"用得越久越省事"的机制——让扣点与回款率的真实粒度是「门店 × 业务大类」的合约常数，既不是活动级单值（跨 12 家店跨两个大类时会被错误复制到每条规则行），也不是规则行级变量（否则同一个问题问 6 遍）。

存储用 SQLite 单文件，零配置、可 diff、可整体导出。

## 6. 架构

- 前端：Vite + React + TypeScript
- 后端：Fastify + TypeScript + better-sqlite3
- 模型：DeepSeek 官方 API，`deepseek-flash`（官方仅暴露 `deepseek-flash` 与 `deepseek-v4-pro` 两个模型；用户所说的 "v4.1 flash" 即前者），`response_format: json_object`
- 单机 `npm run dev` 起两个进程；构建后由 Fastify 托管静态资源

四个模块，其中三个不依赖模型：

| 模块 | 依赖 LLM | 职责 |
|---|---|---|
| generator | 是 | 表单 → 活动方案 + 开单草稿 |
| patcher | 否 | apply / diff / rollback |
| validator | 否 | 17 条规则校验 |
| exporter | 否 | 1811 填写清单 + 界面待选清单 + 1816 核对表 + 中文可视化 |

## 7. 确定性模块

### 7.1 validator 规则清单

来自 PPT 全量审计，含现有 70 字段字典遗漏的条目。

1. `start_date <= end_date`
2. `end_date` 不可为空
3. 活动名称长度约束（口径待确认：1811 占位写"13字內"，1816 标准表写"不能超过13个汉字"，PPT 无证据可裁决）
4. 活动名称与活动内容不含特殊字符（精确白名单未提供，先做保守黑名单并标注）
5. `cycle_weekdays` 取值只能是 0–7，多值用英文逗号分隔
6. `product_scope ∈ {0, 2, 3}` → `outlet_tag_conversion` 必须为 0，否则开单失败
7. `offer_type = 14` → 折扣不得加入 HP 货类
8. `offer_type = 12` → 判断克重不得为 0
9. 判断件数有值 → `offer_type` 必须为 17
10. `trade_in_upgrade_ratio` 只用于以旧换新 / 换购类
11. 区域 / 分区 / 行号三选一互斥
12. 指定货号有值 → 指定牌仔总开关必须置 1（**静默失效防护**：不置 1 则绑定完全不生效、活动按全货品跑、系统不报错）
13. 让扣点与回款率必须被显式回答
14. 让扣点或回款率 > 1 时黄色提醒，不硬拦
15. 多档优惠必须是多条规则行，共用同一 `activity_sequence`，禁止合并单元格
16. 黄金以旧换新 → 提示必须去 1815 把活动分组改为 19)增值服务，否则旧金录不进去；货品回购 → 17)货品回购
17. `discount_rate` 与 `amount_off` 量纲分流检查（打几折 vs 减多少钱）

规则 6、12、16 是现有字段字典完全没有或写窄了的，也是最容易造成"填了却不报错"的三处。

### 7.2 exporter 输出

**主交付：1811 逐字段填写清单**

| ICS 字段名 | 填什么值 | 来源 | 证据年份 | 备注 |
|---|---|---|---|---|

`pending` 的字段单独汇总成"需要你在 1811/1815 界面上选"的清单。

**附带**
- 后置动作清单（活动分组改什么、什么时候改、改不动时怎么办）
- 1816 核对表（13 列 A–M，标注"仅供核对，不可上传"）
- 中文可视化 HTML：活动画像 / 创意与执行 / 评估与系统 / 完整字段四个页签，`null`、`[]`、`{}` 不得隐藏

## 8. LLM 集成

三类调用，全部走 `deepseek-flash` + JSON 模式：

1. **表单 → 活动方案**：few-shot 取同由头的 2–3 条历史活动**完整**塞入 prompt。25 条太少，向量检索没有意义还会引入噪声，按由头建静态索引即可。
2. **自然语言 → patch**
3. **校验失败 → 修正 patch**

写进 system prompt 的硬规则：

- 优惠数值绝不能从历史活动学，只能来自表单输入或用户对话
- 效果指标按由头切换口径，禁止统一写"预计销售额提升 X%"
- 归因禁令：35%–55% 新会员是 Disney+Chiikawa+NBA 组合口径不得单独归因；悟空 20%→40% 是电商口径非全渠道；传承系列 +8%/+350% 是同期表现非活动增量
- 活动名出两套：对外传播名（不限长）+ ICS 开单名（≤13 字、无特殊字符）
- 活动标语进"需法务确认"清单（会打在保证单上）
- 遇到数据集外的品类或玩法，先输出"主数据/枚举是否支持"的前置校验任务，不硬套现有货类

## 9. 修订字段字典

现有 70 字段字典有 4 处建模错误和 8 处遗漏，必须先出修订版，否则所有字段映射建立在一份已知有错的字典上。修订不依赖周大福补料，可立即做。

**拆开被错误合并的条目（拆分 +7，补充 +12，70 → 约 89）**

| 原条目 | 拆成 |
|---|---|
| `threshold_value` | 判断值 / 判断金额 / 判断件数 / 判断克重（四列同时存在、各自取值） |
| `threshold_type` | 减免类型（定额…）/ 判断类型（金额…），两列值域不同 |
| `allowed/denied_product_segment` | 允许产品细分 / 不允许产品细分 / 允许产品板块 / 不允许产品板块（细分与板块是两个维度） |
| `assigned_item_codes` | `assigned_item_mode`（1816 B1 总开关）+ `assigned_items: [{货品编号, 绑定活动序号}]`（多对多） |

**补充遗漏字段（12 个）**：不允许货类、前克优惠金额、余克优惠金额、行名（1816 E 列）、O2O分类（1816 J 列，取值含义未知，留空标红）、使用门槛、是否停止、审批级别，以及 OA 层的 OA 单号、处理意见、回退模式、撤销回退状态。

1816 模板是按列位解析的：少一列，右侧所有列全部错位、整批汇入失败。O2O分类与行名这两列在现有字典里找不到任何对应项。

**修正交叉规则**：转换餐牌规则的触发范围补上货品范围 2（高奖励）与 3（尊享钻石）

**回填已确认的码表**（并标注证据年份与来源图）：审批流 8 项、货品范围 0–6、转换餐牌 0/1、活动分组 3 项、优惠类型 15 个中文名、线上线下 1/2、优惠性质 0/1。现有字典把这些标为 `known_gaps`，是把有证据的东西当成了缺口，会让 agent 在这些字段上无谓追问或拒绝生成。

## 10. 错误处理

| 情况 | 处理 |
|---|---|
| 校验失败 | 列出 JSON 路径与违反的规则编号，不标记为"完整" |
| 模型两轮仍未修好 | 呈现冲突给用户，不静默接受 |
| 枚举值不在已确认码表内 | 降级为 `pending`，写进界面待选清单，不猜 |
| 农历节点日期缺失 | 阻断，要求用户填写，不自行推算 |
| 结束日期为空 | 阻断，要求切子档期 |
| 让扣点/回款率未答 | 阻断，不默认为 0 |
| 数据集外品类 | 输出"需先在 ICS 确认/新增枚举"，不硬映射 |
