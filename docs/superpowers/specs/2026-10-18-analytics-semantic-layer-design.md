# 营销分析语义层重构设计

日期：2026-10-18。状态：待用户确认。范围：只覆盖语义层，编排、答案结构和图表的重构另立文档。

## 1. 为什么先改语义层

2026-10-17/18 用真实模型跑周大福场景（七夕复盘、克减力度、找新角度、会员、金价）。数据库超时解决后，问题集中在三处：每题 30 到 90 分钟，图表和结论脱节，答案没有重点。拆开运行记录 `analysis-runs/*.jsonl` 看，相当一部分时间耗在模型自己摸索业务含义上：

- 「计算引用必须属于相同范围」是四题被拒次数最多的工具错误（S5 一题 15 次）。直接原因是没有日均这类指标，七夕 7 天和其余 24 天只能先各查一次，再用四则运算硬算。
- S2 用了 68 分钟，才得出「两档同窗口是 8 月 22 日到 31 日」。表里本来就有 `活动开始日期`、`活动结束日期`，只是语义层没开放。
- S4 自己定了七夕窗口 8/28–31，但表里 `节庆定义` 写的是「七夕节及前 6 天共 7 天」，对应 8/23–29。
- 现有限制说明写着「没有正式同店定义」，表里却有 `同店类型`，覆盖全部 5934 家门店。
- 现有分区维度用的是 `分区描述`。A 到 H 区在东、南、西、北 4 个大区都存在，按它分组会把 4 个同名分区合成一组。

结论：语义层现在主要说「不能怎么用」，很少说「这是什么」。模型拿不到业务结构，只能试错，试错又触发拒绝和复核退回。

## 2. 约束

1. 模型不写 SQL。模型提交语义查询（指标、维度、筛选、对照），由 TypeScript 编译成参数化 SQL。数字守卫和证据引用继续建立在代码计算之上。
2. 只读。账号 `ctf_agent_ro` 只有 SELECT。不改客户表；本地演示另建的投影表 `sales_analysis_202508` 是源表字段子集，行数、金额、毛利、克重、订单数和整行哈希都已和源表核对一致。
3. 模块边界沿用 `CLAUDE.md`：`app/lib/analytics` 下的共享模块不 import npm 包，相对 import 写 `.ts`，不用 enum。
4. 每个语义定义都标依据。依据分四档：`schema`（字段名或类型）、`data`（本文实测）、`business`（周大福确认）、`assumption`（推断）。`assumption` 级的定义可以用来查数，但答案里必须显示「口径待确认」。这条借自 jm 语义层的 evidence 分级。
5. 码值不猜。码值含义只来自实测或业务确认，测不出来的写进第 9 节待确认清单。

## 3. 不复用 jm 语义层

jm 的语义层（`~/Desktop/jm/docs/superpowers/plans/2026-09-13-semantic-layer.md`）面向未知的多表客户库：零人工、LLM 生成自然语言说明，Agent 直接写 SQL（`ConnectorToolExecutor.java:783`）。它没有维度、度量、层级、派生指标这些结构，而且口径公式明确禁止由机器给出（`semanticContract.ts:62-66`）。

这里是一张已知宽表，需要的正是可计算的业务结构，所以不复用。借用三条纪律：依据分级、码值不猜、口径经人确认后沉淀。

## 4. 数据事实（2026-10-18 实测）

源表 `sales_detail_202508`：157 列，1,287,840 行，日期 2025-08-01 到 08-31，币种只有人民币。

### 4.1 门店层级

| 关系 | 实测 | 结论 |
|---|---|---|
| 区域 → 大区 | 每个区域编码只属于 1 个大区 | 区域可以嵌在大区下 |
| 分区编码 → 区域 | 同一分区编码最多出现在 5 个区域 | 分区编码不唯一，必须和上级组成复合键 |
| 小区 → 大区 + 分区 | 每个小区只属于 1 个「大区 + 分区」 | 「大区 + 分区」组合（55 个）是有效层级 |
| 小区 → 区域 | 有小区属于 2 个区域 | 小区不严格嵌在区域下 |
| 门店 → 小区、商场集团、同店类型 | 都是唯一 | 都可以作为门店属性 |
| 城市 → 省份 | 唯一 | 可以嵌套 |

确定的层级：大区（4）→「大区 + 分区」（55）→ 小区（351）→ 门店（5934）。区域（16，例如「湘鄂(A-E区)」「京津鲁晋(A-G区&R区)」）是大区下面的另一条分组路径，名字里列出了它包含的分区。区域和「大区 + 分区」的关系并不完全一致，见待确认 Q3。

### 4.2 门店属性

可开放、取值有限的字段：

- 分店性质（4）、性质分组（2）、同店类型（3：同店 5459 家、非同店(续存) 388 家、非同店(非续存) 86 家）
- 城市级别（6）、省份（31）、城市（330）
- 商场集团（1494，其中街铺单独一类）、铺型（3）、店铺组成（5）
- 形象级别（6）、销售级别（7）、分店级别（4）、分店形象（32）、零售体验（9）
- 分店面积区间（10）、店龄（26 档，0 到 25 年）

只有 1 个取值、没有分析价值的字段：分店渠道、门市渠道、店铺存货类型描述。

### 4.3 时间

- `周末标识`、`周日标识`、`工作日标识`：8 月工作日 21 天，周六 5 天，周日 5 天。三列互斥且完整。
- `节庆`：只有「七夕节」一个取值，覆盖 35.9% 的行，日期 8/23–29，与 `节庆定义` 一致。

### 4.4 货品

- 业务小类（15）、材料（29）、材料组别（13）、组别大类（18）、组别小类（22）、价位段（18 档，从 <500 到 >=1000k）

- `业务小类 → 组别大类` 不是一对一（最多对应 12 个），所以两者是并列的两条分类，不是层级。

### 4.5 活动

- `优惠小类`：551 个取值，空值 2.3%。一张单可能用到多个优惠：1 个的 897,909 单，2 个的 17,746 单，3 个及以上的 436 单。
- `营销活动`：总部营销活动、地区营销活动两类。
- `活动开始日期`、`活动结束日期`：同一个优惠名会有多个周期。例如 H-克减30元 的主周期是 8/1–8/22（3,109 行）和 8/22–9/1（119,688 行），另有 2024–2025 年的零星行。

| 销售 | 件数 > 0 且实收 > 0 | 1,138,024 | 87.28 亿 |

### 4.7 金额

- `零售毛利` 不等于 `实收 - 成本`：在 113.8 万行销售里，只有 100 行吻合，按去税 13% 算也只有 334 行吻合。毛利是源系统另算的口径，不能自己推导（Q2）。
- `销售牌仔价` 与 `销售一口价` 有 151,858 行不同。一般足金类两者汇总相等，都是 61.21 亿。
- 销售行的实收占牌仔价比例：一般足金类 97.55%，定价黄金类 95.76%，钻石类 94.75%，宝石类 89.20%。
- 一般足金、足金的每克牌仔价：8/1 是 1081.5 元，8/15 是 1091.5 元，8/31 是 1100.0 元，月内上涨约 1.7%。
- `源行分店店号 ≠ 实体分店店号` 的有 561,862 行（33.45 亿），但源行和实体店的大区都一致。推断源行是货品来源店（Q6），本次不开放。

## 5. 语义模型

一个文件 `app/lib/analytics/semantic/model.ts`，纯数据，不放逻辑。它是数据库编译器、能力目录、提示词和答案限制说明的唯一来源。

### 5.1 类型

```ts
type Basis = "schema" | "data" | "business" | "assumption";
type Provenance = { basis: Basis; note: string };          // note 写实测数字或确认人和日期

type Dimension = {
  id: string; label: string;
  key: string[];                // 复合键列，例如 ["大区编码", "分区编码"]
  display: string[];            // 展示用列，例如 ["大区描述", "分区描述"]
  parent?: string;              // 层级上一级的 dimension id
  entity: "store" | "time" | "product" | "offer" | "line";
  cardinality: number;          // 实测去重数，扫描时用于分组上限
  scan: boolean;                // 是否纳入「找新角度」的扫描空间
  provenance: Provenance;
};

type Measure = {                // 可加总的基础度量，直接 SUM 或 COUNT
  id: string; label: string; unit: string;
  sql: "sum" | "count_distinct";
  column: string | string[];
  provenance: Provenance;
};

type Metric = {                 // 给模型和业务看的指标
  id: string; label: string; unit: string;
  numerator: string;            // measure id
  denominator?: string;         // measure id，或 "days" 表示期间天数
  transform?: "one_minus";      // 折扣率 = 1 - 实收 / 牌价
  population: LinePopulation;   // 默认行口径
  requires?: string[];          // 必须同时控制的维度，例如每克指标要求货类和材料
  definition: string;           // 一句话口径，答案里直接引用
  provenance: Provenance;
};

type Baseline = {               // 可直接选用的对照
  id: string; label: string;
  kind: "filter" | "period" | "same_store";
  definition: string; provenance: Provenance;
};
```

### 5.3 基础度量

实收、件数、金重、零售毛利、牌仔价、成本、订单（门店 + 销售单号去重）、门店数、行数、天数（期间内去重日期数）。

### 5.4 指标

| 指标 | 公式 | 默认口径 | 依据 |
|---|---|---|---|
| 实收 | SUM(实收) | 销售 | data |
| 净实收 | 销售 + 零元销售 + 退货（不含回收） | 净额 | data，回收是否扣除见 Q4 |
| 日均实收 | 实收 / 天数 | 销售 | data |
| 日均订单 | 订单 / 天数 | 销售 | data |
| 单均 | 实收 / 订单 | 销售 | data，订单只覆盖筛选内成交 |
| 件均 | 实收 / 件数 | 销售 | data |
| 毛利率 | 零售毛利 / 实收 | 销售 | assumption，毛利口径见 Q2 |
| 折扣率 | 1 − 实收 / 牌仔价 | 销售 | assumption，牌仔价是否就是标价见 Q8 |
| 每克实收 | 实收 / 金重 | 销售，要求控制货类和材料 | data |
| 每克牌价 | 牌仔价 / 金重 | 销售，要求控制货类和材料 | data，用作金价代理指数，不等于当日金价 |
| 会员销售占比 | 会员实收 / 实收 | 销售 | data |

比率指标一律按分子、分母分别汇总后再相除，不平均各组的比率。日均的分母是该范围内实际有成交的天数，范围的天数在证据里单独列出。

### 5.5 对照基线

| 基线 | 含义 | 依据 |
|---|---|---|
| 一般開單 | 同期、同范围内优惠为「一般開單」的成交 | assumption，见 Q1 |
| 同店 | `同店类型 = 同店` 的门店 | schema + data，口径见 Q9 |
| 非活动日 | 同月里不在目标活动周期内的日期，按日类型对齐 | data |
| 非节庆日 | `节庆` 为空的日期，按日类型对齐 | data |
| 同周期共同门店 | 两个对象在同一周期内都有成交的门店 | data，是现在「共同观察门店」的正式定义 |

### 5.6 活动实体

活动 = `优惠小类` + `活动开始日期` + `活动结束日期`。同一个优惠名的不同周期视为不同的活动期次。语义层提供：

- `listOffers(filter)`：返回优惠名、营销活动类型、各期起止日期、每期行数、门店数和实收。供模型选活动、对齐窗口用。
- 行数少于阈值的期次（例如 2024 年 11 月那批零星行）标记为「跨期零星」，默认不参与比较。阈值属于 assumption。

## 6. 查询接口与编译

模型通过工具提交语义查询：

```ts
type SemanticQuery = {
  metrics: string[];                       // metric id
  by?: string[];                           // dimension id，最多 3 个
  filters?: Record<string, string[]>;      // dimension id → 取值
  period: { start: string; end: string } | { offer: string; edition?: string } | { festival: string };
  baseline?: string;                       // baseline id，生成 目标 / 参照 / 差额 / 相对变化
  population?: LinePopulation;
};
```

编译器（`agent/semantic-compiler.ts`）的规则：

1. 期间可以写日期，也可以写「某活动某期」或「某节庆」，由编译器换算成日期范围和过滤条件。这样模型不用再自己去找活动窗口。
2. 复合键维度按键分组、按展示列输出。同名分区天然分开，不再合并。
3. 比率指标在同一条 SQL 里同时取分子和分母，输出比率，也保留分子和分母，供证据核对。
4. 有 baseline 时，一次查询同时算目标和参照，按维度配对，输出差额和相对变化。原来「两个范围各查一次再四则运算」的路径就此消失，「计算引用必须属于相同范围」这条拒绝也就不会再触发。
5. 维度和指标的 requires 不满足时，编译器直接报错，并说明缺了哪个控制条件。
6. 查询结果写入现有证据注册表。证据里的口径说明、依据档位从语义模型生成，不再在各处手写。

现有的五种分析操作（汇总、对照、拆解、扫描、稳健性）保留，但都改为接收语义查询。扫描的分组空间改为维度清单中 `scan: true` 的维度，并沿用样本量门槛。

## 7. 限制说明怎么生成

现在每个方法都会拼一段口径说明，一份答案里同一句「共同观察门店不是正式同店」重复了 4 次。改成：

- 每个指标、维度、基线只有一句 `definition`。
- 答案只列本次实际用到的定义，按 id 去重。
- 依据是 `assumption` 的项，统一放到「口径待确认」一栏，不散落在正文里。
