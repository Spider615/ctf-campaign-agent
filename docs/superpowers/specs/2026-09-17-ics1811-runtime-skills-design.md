# ICS-1811 运行时 Skill 生态设计

日期：2026-09-17

状态：已完成口头设计确认，待书面规格审阅

本文补充 `2026-09-16-ics1811-sop-agent-design.md` 与 `2026-09-16-conversational-build-design.md`，只调整 Agent 获取解释性业务知识的方式，不改变事实层、1811 填写值、校验或落库规则。若本文与前两份文档在「业务知识应放在提示词还是 Skill」上冲突，以本文为准；确定性业务行为仍以前两份文档和领域代码为准。

## 1. 背景

当前 Agent 的系统提示词同时承担回合协议、工具说明、字段解释、玩法知识和文案规范。继续增加规则会带来三个问题：

- 每一轮都携带与当前问题无关的知识，浪费上下文；
- 规则散在提示词、领域代码和文档中，维护者难以判断应改哪一处；
- 模型的解释性知识与代码执行规则混在一起，容易让软性说明被误认为业务真相。

当前工作树已经有本地插件、Skill 目录扫描和 Skill 轨迹的未完成骨架，但 `agent/plugin/skills/` 仍为空。提示词中的部分知识已经删去，因此实现必须一次补齐 Skill 内容、校验、调用和测试，不能保留「规则已移走但 Skill 为空」的中间状态。

## 2. 目标与非目标

### 2.1 目标

1. 用 Claude Agent SDK 的本地插件和原生 `Skill` 工具，按场景加载 ICS-1811 解释性业务知识。
2. 第一版只整理仓库里已有、可追溯到设计文档、操作指引、截图提取或确定性实现的规则。
3. 开发者在仓库中编辑 `SKILL.md`，通过 Git 评审、静态校验和测试发布。
4. 新增或修改合法 Skill 后，下一回合自动生效，不要求重启 Agent 服务。
5. 让用户在执行记录中看见「加载了哪份业务规则」，但不暴露完整规则、系统提示词或隐藏思维。

### 2.2 非目标

- 不建设运营规则管理后台、数据库表、远程 Skill 市场或在线编辑能力。
- 不允许 Skill 写草稿、改事实、决定缺项、生成最终填写值或绕过工具守卫。
- 不把行业常识、模型推断或尚未确认的业务说法包装成规则。
- 不把门店、货类、优惠类型等代码表复制进 Skill。
- 第一版不开放 `Read`、`Bash` 或其他文件和命令行工具，也不使用多层引用文件。

## 3. 真相层级与职责边界

运行时按以下顺序裁决冲突：

1. **确定性代码与业务工具结果**：唯一执行真相；
2. **带仓库出处的 Skill**：用于解释、建议、问法和文案指导；
3. **模型的一般知识**：只能用于自然表达，不能补业务规则。

Skill 与工具结果不一致时，模型必须按工具结果继续，并用用户能理解的语言如实说明。Skill 不能声称某项已经保存、活动已经完整或某个取值已经通过校验；这些状态只来自工具。

以下内容必须保留在 TypeScript 中：

| 规则类型 | 唯一执行位置 |
|---|---|
| 事实结构与来源 | `app/lib/campaign/ics1811/types.ts`、`facts.ts` |
| 原话证据、数字和日期换算 | `facts.ts`、`phrases.ts` |
| 玩法识别与参数范围 | `offer-spec.ts` |
| 填写值推导 | `derive.ts`、`fill-sheet.ts` |
| 缺项、问题题号和完成状态 | `questions.ts` |
| blocker / warning | `checks.ts` |
| 代码表与名称解析 | `codebook.ts`、`resolve.ts` |
| 提议、点头、工具参数和撤销 | `proposals.ts`、`card.ts`、`app/lib/agent/tools.ts` |
| 回合编排与落库 | `app/lib/server/turns.ts`、`session-store.ts` |

安全红线可以有意重复：Skill 提前指导模型，TypeScript 最终拦截可穷举的高风险形式。例如宣传文案不得虚构权益写入 `promo-copy-guide`，文案工具继续拦截赠品、好礼、抽奖、免费、加赠、豪礼和礼包等已有词形。工具守卫不是自然语言事实核验器，未穷举的改写仍由 Skill 指导和评审场景覆盖，不能声称所有虚构权益都能被代码识别。

## 4. 插件与目录结构

```text
agent/plugin/
├── .claude-plugin/
│   └── plugin.json
└── skills/
    ├── offer-entry-guide/
    │   └── SKILL.md
    ├── field-explainer/
    │   └── SKILL.md
    ├── settlement-guide/
    │   └── SKILL.md
    └── promo-copy-guide/
        └── SKILL.md
```

插件名固定为 `ics1811`。SDK 中的限定名分别为：

- `ics1811:offer-entry-guide`
- `ics1811:field-explainer`
- `ics1811:settlement-guide`
- `ics1811:promo-copy-guide`

`agent/skills.ts` 负责发现、读取和校验目录；`agent/server.ts` 只消费校验后的目录，不自行解析 Skill 文件。四个基线 Skill 缺少任意一个都视为目录损坏。以后新增合法 Skill 可以自动加入精确白名单，无须再改服务端注册代码；删除或改名基线 Skill 则必须同步修改基线清单和测试。

## 5. 四个基线 Skill

### 5.1 `offer-entry-guide`

**触发场景**：用户询问某种优惠玩法如何在 1811 录入、固定与浮动模式如何选择、特殊换购活动怎样处理，或者某种玩法是否超出 1811 范围。

**包含内容**：

- 1811 的用途和适用范围；
- 已有材料明确支持的玩法及白话录入说明；
- 固定/浮动折扣模式、累加、克重口径、转餐牌等操作含义；
- 黄金以旧换新、铂金以旧换新、钻石以小换大、买钻石享黄金克减等特殊场景；
- 抽奖、签到等不带成交优惠的活动无法通过 1811 录入时的说明；
- 创建后需要去 1815 修改活动分组等已有出处的后续操作。

**不包含**：玩法到最终字段值的可执行映射、参数范围校验、代码值列表。这些只由 `offer-spec.ts`、`derive.ts` 和工具返回。

### 5.2 `field-explainer`

**触发场景**：用户询问字段或名词含义，或者在回答某个缺项前需要理解为什么要问。

**包含内容**：

- 计折上折、固定/浮动折扣模式、让扣点、回款率；
- 货品范围、货类、货类明细、售价类型、限制条件、活动分组；
- 为什么需要运营确认某个人定字段；
- 面向运营的白话解释和不带默认值的自然问法。

**不包含**：问题题号、缺项算法、短回答归属、默认值或代码表选项。用户说「不知道」「按惯例」时仍由事实守卫和问题规划处理。

### 5.3 `settlement-guide`

**触发场景**：多家门店、跨区域、结算说明函、文件命名或上传流程。

**包含内容**：

- 单店、多店和跨区域场景中，现有材料已经明确的处理说明；
- 多店活动上传结算说明函的指引；
- 文件命名顺序、数量和不重名要求；
- 材料存在矛盾或未给出结论时，怎样明确告诉用户「现有指引不能确认」。

**不包含**：单店是否必须上传、跨月取哪个月份等尚无确定结论的断言；也不复制门店代码。需要识别门店时仍调用确定性查询工具。

### 5.4 `promo-copy-guide`

**触发场景**：用户要求起草、修改或评价对外宣传文案，或者讨论活动标语。

**包含内容**：

- 对外文案的目标、语气和结构；
- 主标题、卖点与代码生成的优惠说明如何分工，避免重复；
- 不承诺活动事实中不存在的赠品、抽奖、免费服务或其他权益；
- 标语只能使用用户提供且经法务确认的原文；
- 正式发布前仍需法务确认的提示。

**不包含**：最终日期、门店和优惠说明的渲染，也不放宽标题、卖点、数字或虚构权益的工具守卫。

## 6. `SKILL.md` 合同

### 6.1 元数据

第一版只支持单行 `name` 和 `description`：

```markdown
---
name: offer-entry-guide
description: 解释 ICS-1811 优惠玩法、录入方式和不支持场景。用户询问打折、满减、克减、以旧换新、以小换大、固定或浮动折扣模式以及 1811 如何录入时使用。
---
```

要求：

- `name` 使用小写字母、数字和连字符，最长 64 个字符；
- `name` 必须与目录名一致且在插件内唯一；
- `description` 非空、最长 1024 个字符，同时写清「做什么」和「何时使用」；
- 不设置 `disable-model-invocation`，因为这些 Skill 需要由模型按场景自动加载；
- 不接受未知元数据字段，避免手写解析器静默误读。

### 6.2 正文结构

四个文件统一包含：

```markdown
# 标题

## 适用场景
## 回答原则
## 业务知识
## 不能做什么
## 冲突处理
## 出处
```

每个文件必须自包含且不超过 500 行。第一版不链接 `reference.md`、示例文件或脚本，因为运行时只开放原生 `Skill` 工具，不开放继续读取文件的能力。

### 6.3 来源标记

`适用场景`、`回答原则`、`业务知识`、`不能做什么` 和 `冲突处理` 下的每个规则条目必须带一个或多个来源编号，例如：

```markdown
- 多家分店活动按指引上传结算说明函。[S1]

## 出处

- [S1] `references/ppt-operation-guide.txt` — 结算说明函段落
```

来源要求：

- 只允许仓库相对路径，可附章节、符号名或文字定位；
- Git/CI 校验时，被引用路径必须存在；生产运行时不要求部署这些来源文件；
- 每个正文来源编号必须在 `出处` 中定义，未使用的来源编号也报错；
- 不接受外部 URL、`TODO`、`TBD` 或「以后补」式占位；
- 材料只能支持到「无法确认」时，Skill 就明确说无法确认，不把开放问题补成规则。

frontmatter 的 `description` 是给 SDK 使用的发现摘要，不放来源编号。`适用场景` 的第一条必须逐字重复 description，再追加来源编号；这样静态校验可以确认发现摘要有来源，后续条目再补充更细的触发边界。来源编号只用于维护和审计，正常回答不向用户朗读 `[S1]` 之类的内部标记。静态校验只能验证格式和路径存在；规则是否忠实于来源仍由 Git 评审负责。

## 7. 发现与校验

`agent/skills.ts` 提供运行时入口 `loadSkillCatalog(pluginDir)`，成功时返回按名称排序的只读目录，失败时抛出带相对文件路径和具体原因的 `SkillCatalogError`。它同时提供供测试和 CI 使用的 `validateSkillSources(catalog, repoRoot)`；只有后者读取 Skill 所引用的仓库来源文件。

每一回合创建 SDK 查询前重新读取目录，因此合法的 `SKILL.md` 修改在下一回合生效。校验顺序为：

1. 插件清单存在且插件名为 `ics1811`；
2. `skills/` 存在，四个基线 Skill 齐全；
3. 每个 Skill 目录恰有一个可读的 `SKILL.md`；
4. frontmatter、名称、描述、重复名和目录名合法；
5. 一级标题和六个必需章节齐全且不重复，`适用场景` 首条在移除来源编号后与 `description` 完全一致；
6. 文件行数、来源编号和来源写法合法；
7. 目录中所有合法 Skill 组成当前回合的精确白名单。

Git/CI 另外调用 `validateSkillSources`，确认每个仓库相对路径确实存在。生产部署只需携带插件和 Skill 文件，不需要为了运行时校验打包 `docs/`、`references/` 或领域源码。

不再使用「读不到就返回空数组」的静默降级。插件或 Skill 目录损坏是开发或部署错误，本回合通过现有 `agent_error` 路径明确失败，避免模型在缺少规则时凭印象继续。

## 8. SDK 集成与运行流程

`agent/server.ts` 使用当前已锁定的 `@anthropic-ai/claude-agent-sdk` 版本提供的一等 `plugins` 和 `skills` 选项：

```ts
{
  tools: ["Skill"],
  plugins: [{ type: "local", path: PLUGIN_DIR }],
  skills: catalog.map((skill) => `ics1811:${skill.name}`),
  settingSources: [],
  allowedTools: AGENT_TOOL_NAMES.map((name) => `mcp__campaign__${name}`),
}
```

约束如下：

- `settingSources: []` 保持 SDK 隔离，不读取开发者个人或项目 Claude 配置；显式本地插件仍可加载；
- `skills` 始终是校验后目录生成的精确列表，不使用 `all`；
- `tools` 只开放 SDK 内置 `Skill`，不开放文件、命令行或其他开发工具；
- `allowedTools` 只列业务 MCP 工具，不再把 `Skill` 当成业务权限项；
- 默认插件传输方式保持 `argv`；
- `maxTurns` 从 10 调整为 12，为一次 Skill 加载预留工具往返；120 秒单轮超时不变，并由场景测试观察是否足够。

运行顺序：

1. 收到用户消息；
2. 读取并校验 Skill 目录；
3. 创建带本地插件和精确 Skill 白名单的 SDK 查询；
4. 服务把确定性路由识别出的必需 Skill 告诉模型，模型也可以根据名称和描述加载其他相关 Skill；
5. 服务记录 Skill 的开始和完成状态；
6. 模型按需调用活动工具；
7. TypeScript 守卫、推导和校验决定真实业务结果；
8. 模型基于 Skill 知识和工具结果回复。

Skill 内容不跨回合保存。模型上一轮加载过的规则，下一轮需要时必须重新加载。

## 9. 路由与强制前置条件

系统提示词只保留 Skill 路由，不复制 Skill 正文。`agent/skills.ts` 另外提供纯函数 `requiredSkillsForTurn(request)`：它只识别明确的解释、录入指导、结算咨询和文案任务，返回本回合必须成功加载的 Skill；普通事实陈述不因为出现一个领域名词就自动命中。

| 用户意图 | 应加载 Skill |
|---|---|
| 询问玩法、录入方法或是否支持 | `offer-entry-guide` |
| 询问字段或名词含义 | `field-explainer` |
| 询问多门店、跨区域或结算说明函的处理方式 | `settlement-guide` |
| 起草、修改或评价宣传文案、讨论标语 | `promo-copy-guide` |
| 清晰地提供日期、门店、优惠等事实 | 不加载无关 Skill |

固定/浮动折扣模式同时出现在玩法和字段知识中，按用户意图区分：

- 问「是什么意思」「有什么区别」时只要求 `field-explainer`；
- 问「这个活动怎么录」「该选哪个模式」时只要求 `offer-entry-guide`；
- 同时要求解释含义并给出录入选择时，两者都要求加载。

同一回合可以加载多个 Skill，但只加载当前请求实际涉及的内容。解释性问题可以不调用活动工具，却仍须先加载对应 Skill；提示词中原有「解释性问题直接回答，不调工具」改成「不调活动工具，需要业务知识时仍加载 Skill」。

服务维护当前回合的 `loadedSkills` 集合和 `skillLoadFailed` 标记：原生 `Skill` 工具成功返回时加入集合，任一 Skill 失败或请求未知 Skill 时设置失败标记。必需 Skill 名称随本轮用户提示一起传给模型；SDK 返回成功结果后、调用 `finishAgentTurn` 之前，服务检查必需集合是否全部加载，并确认本回合没有 Skill 加载失败。任一条件不满足就把本回合判为 Agent 合同错误，不向用户返回可能无出处的知识回答。加载失败后的重试发生在用户下一回合，避免把失败前后的不完整知识混进同一次回复。

`draft_promo_copy` 还执行更早的工具级检查：`promo-copy-guide` 没有成功加载时返回可重试的工具错误，要求模型先加载规则再重新起草。文案工具原有的数字、长度和已列高风险权益词形守卫继续保留。

确定性路由只决定「这轮至少要加载什么」，不直接读取 Skill 正文、不替模型回答，也不决定业务字段值。没有命中必需路由时，模型仍可根据 Skill 描述主动加载相关知识；真正改变数据的行为仍由业务工具强制。

## 10. 执行记录与隐私

原生 Skill 工具不经过业务 MCP handler，服务从 SDK 消息流中配对 `tool_use` 与 `tool_result`：

- 工具名统一记为 `load_campaign_skill`；
- 标题为「加载业务规则：{Skill 一级标题}」；
- 成功摘要为「已读取这份规则」；
- 失败摘要为「规则没有加载成功」；
- 只记录名称、状态、发起方和耗时，不记录 Skill 正文、系统提示词或完整工具输入。

配对键使用 SDK 的 `tool_use_id`。回合结束时仍未完成的 Skill 轨迹统一收束为 warning，避免实时界面永久停在 started。未知 Skill 名称按 warning 记录，同时由 SDK 精确白名单拒绝调用。

现有通用工具步骤 UI 继续展示该轨迹，不增加专用卡片或数据库字段。旧会话不含此工具名，解码行为不变。

## 11. 失败策略

| 失败 | 行为 |
|---|---|
| 插件目录、基线 Skill 或元数据损坏 | 本回合失败，写现有 `agent_error`，提示开发者修正规则包 |
| 模型请求未知、未启用或加载失败的 Skill | 轨迹记 warning，本回合最终写可重试的 `agent_error`，用户下一回合重试 |
| 路由标记为必需的 Skill 加载失败或被模型漏掉 | 回合后置校验失败，不返回知识回答，写可重试的 `agent_error` |
| 起草宣传文案但未加载文案 Skill | 文案工具拒绝并提示先加载；加载后可在同一回合重试 |
| Skill 与业务工具结果冲突 | 以工具结果为准，并向用户说明实际可执行结果 |
| Skill 轨迹只有 started | 回合结束时转为 warning，不写入悬空状态 |

Agent 失败时沿用现有回合事务语义：用户输入不丢，写一条可重试的 `agent_error`；Skill 不引入独立持久化状态。

目录完整且 `requiredSkillsForTurn` 返回空数组时，普通事实录入不调用 Skill，继续依靠确定性业务工具处理。目录本身损坏则所有回合都失败；不能以「这轮可能用不上」为由绕过损坏的发布产物。

## 12. 测试设计

### 12.1 静态目录测试

新增 `tests/skills.test.ts`，用临时夹具覆盖：

- 四个基线 Skill 和新增 Skill 的正常发现、排序与限定名；
- 空目录、缺少基线 Skill、缺少 `SKILL.md`；
- frontmatter 缺失、未知字段、非法名称、目录名不一致、空描述、重复名；
- 缺少章节、超过 500 行；
- 来源未定义、未使用、来源写法错误、外部 URL 和占位文字；
- CI 来源校验能发现仓库路径不存在，但运行时目录加载不依赖来源文件随部署产物存在；
- `skillOf` 对限定名、短名称和未知名称的处理。

### 12.2 运行逻辑测试

- `load_campaign_skill` 能通过轨迹解码、合并、完成、失败和旧消息兼容测试；
- 未完成 Skill 轨迹在回合结束时变为 warning；
- 精确白名单只包含插件目录中校验通过的 Skill；
- `requiredSkillsForTurn` 覆盖四类明确意图、普通事实输入、混合意图和固定/浮动模式的路由优先级；
- 必需 Skill 被漏掉或加载失败时，回合后置校验拒绝模型回复；非必需 Skill 不影响普通事实录入；
- 模型主动加载的非必需 Skill 若失败，回合后置校验同样拒绝回复；
- `promo-copy-guide` 未加载时文案工具被拒，加载后允许执行；
- Skill 失败不改变草稿、事实、填写值或版本；
- 普通事实录入不要求先加载 Skill。

默认单测不调用模型、不需要 API Key。涉及 SDK 消息的部分使用合成消息或抽出的纯函数测试，延续现有脚本化假 Agent 的做法。

### 12.3 场景验收

| 输入 | CI 合同断言 | 真实 SDK 验收 |
|---|---|---|
| 「计折上折是什么意思」 | 必需集合为 `field-explainer`；缺失则回合失败 | 模型实际加载后再解释，不调用修改草稿的工具 |
| 「黄金以旧换新在 1811 怎么录」 | 必需集合为 `offer-entry-guide` | 模型实际加载并按已有指引解释 |
| 「两家店要不要说明函」 | 必需集合为 `settlement-guide` | 模型实际加载且不补材料未确认的规则 |
| 「帮我写一版宣传文案」 | 必需集合为 `promo-copy-guide`；工具前置检查生效 | 模型先加载再调用文案工具 |
| 「浮动和固定有什么区别」 | 只要求 `field-explainer` | 模型解释含义，不擅自替用户选择 |
| 「这个活动该选浮动还是固定，1811 怎么录」 | 只要求 `offer-entry-guide` | 模型结合已有活动事实给录入指导 |
| 「先解释区别，再告诉我这个活动怎么录」 | 同时要求字段与玩法 Skill | 模型加载两份且不混淆权威层级 |
| 「10 月 1 日到 7 日，7590 店，钻石 95 折」 | 必需集合为空 | 模型不加载无关 Skill，正常抽取事实 |
| 必需 Skill 加载失败 | 后置校验拒绝回复 | 用户只收到可重试错误，不收到猜测答案 |
| Skill 文字与工具返回冲突 | 合同固定工具优先 | 回复采用工具结果 |

CI 合同断言使用纯函数、合成 SDK 消息和脚本化假 Agent，不声称证明模型行为。另提供一组需要有效模型密钥、默认不进 CI 的真实 SDK 验收测试，至少覆盖表中的四类基线 Skill、一个无 Skill 的普通事实回合及一个加载失败回合。它用于 SDK 升级和发布前验证，不替代确定性单测。

## 14. 上线与回退

实现按以下顺序落地，始终保持主路径可验证：

1. 写四个 Skill 和严格目录校验，先让静态测试通过；
2. 完成 SDK 白名单、Skill 轨迹和文案前置条件；
3. 收窄系统提示词并补运行逻辑与场景测试；
4. 更新部署和开发文档，运行全量验证；
5. 使用有效模型密钥执行一次可选冒烟测试。

确定性领域代码不依赖 Skill，因此回退只需整体回退本功能的提示词、插件加载和 Skill 文件，不需要迁移数据或修复已有会话。不能只删除 Skill 文件而保留已经收窄的提示词。

## 15. 已确认决策

- 只建设运行时业务 Skill，不同时建设开发协作 Skill。
- 第一版只采用仓库已有且有出处的规则。
- Skill 由开发者在仓库中维护，走 Git 评审和测试。
- 按四个业务场景拆分，不做单一巨型 Skill，也不按每个字段细拆。
- 解释和写作知识进入 Skill；确定性业务规则继续由代码执行。
- 每个 `SKILL.md` 自包含，第一版只开放原生 `Skill` 工具。
- 目录或元数据损坏时明确失败；知识加载失败时不猜测。
- 宣传文案起草必须先成功加载 `promo-copy-guide`。
