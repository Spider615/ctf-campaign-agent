# 深度剖析：按时间范围重算图谱（节日筛选）设计

日期：2026-11-07
状态：已确认，待出实施计划
关联：`2026-10-20-insight-drivers-design.md`（图谱本身）

## 1. 要解决的问题

运营想看「某个节日期间，哪些因素影响了销售额、毛利、销量」。现在的图谱固定用整月数据，节日只是「七夕」一个节点，看不出节日期间门店之间、活动之间的差别。

本设计只回答**节日期间内部**的问题（方案 A）：把图谱限定到一段日期重算，看这段时间里各因素对三个指标的影响。不回答「哪些因素决定一家店被节日拉动多少」（方案 B，需要单独的「拉动倍数」指标，等有了不与大促重叠的节日数据再做）。

## 2. 数据事实（2026-11-07 查 `sales_analysis_202508`）

- 数据只覆盖 2025-08-01 至 08-31。`节庆` 字段唯一取值是「七夕节」，覆盖 8/23–8/29 共 7 天；8/29 当天销售额 11.07 亿，平常周末 2–3 亿。
- 全国克减铺开日（`drivers.ts` 按金额推出）是 8/22。七夕 7 天全部落在克减期内，**数据里分不开节日效应和活动效应**，页面必须写明。
- 七夕 7 天正好周一到周日各一天。

## 3. 范围与入口

- URL 加 `from`、`to`（`YYYYMMDD`），不带就是全月；和 `mode`、`node`、`edge`、`source` 并存，可分享。
- 时间控件在深度剖析图上方：下拉为「全月」+ 节日预设 + 「自定义」（起止日期）。
- 节日预设不写死日历，由图谱返回：按 `节庆` 取值分组，取每个节日的最早、最晚日期。现在只有「七夕 8/23–8/29」。
- 范围校验在 Agent 侧：8 位日期、`from ≤ to`、落在数据起止日期内、跨度至少 3 天。不合格返回 400 和中文原因，页面展示原因，不静默回退全月。日期通过校验后以查询参数传入 SQL，不拼接字符串。
- 图谱问答（`/insight/ask`）带同一个范围，依据材料来自同一张图。从图谱跳到智能问答时，`focusContext` 写明范围。

## 4. 查询（`agent/insight-graph.ts`）

- 门店日面板、门店属性、货类、计价金分组、克重门槛、以旧换新、范围（scope）这几条加 `交易日期wid BETWEEN ? AND ?`。
- 逐日查询始终取全月（约 31 行），交给 `drivers.ts` 标出窗口内外。克减铺开日、平日对照组都从全月逐日数据里取。
- 缓存：磁盘缓存键改为「数据版本 + SQL + 参数」，不同范围自然分开。内存缓存从单份改为按范围的 Map，最多保留 8 份，超出按最久未用淘汰；同一范围的并发请求共用一个计算。启动预热只算全月。

## 5. 图谱计算（`app/lib/insight/drivers.ts`）

- `DriverData` 增加 `window: { from, to } | null`（null 为全月）。
- 「开满 20 天的店」：全月保持 20 天，全月图的数字不变；窗口不是全月时改为 `ceil(窗口天数 × 2/3)`，七夕 7 天 → 5 天。所有写着「开满 20 天」的文案改为按实际门槛填。离群店里「营业天数少、算数据不完整」的门槛同样缩放：全月保持不到 10 天，选了范围时为不到 `ceil(窗口天数 / 3)` 天。
- 新增「这个范围内不适用」：节点和连线照常画但置灰，不给分数和强弱，`basis` 写明原因。判定：
  - 「七夕」：窗口内全是节日日，或一天节日日都没有（把「非节日」也算一种取值，窗口内取值少于 2 种）。
  - 「星期」：窗口内任一出现的星期值少于 2 天。
  - 「新增还是挪动」：窗口外、铺开日之前没有周一、三、四的平日。
- 「新增还是挪动」的对照：窗口不是全月时，「之前」取窗口外、铺开日前不过节的周一、三、四，「之后」取窗口内铺开日起的周一、三、四（和全月一样去掉节日当天）；全月时保持现有口径。依据里写明对照期日期。「之前」或「之后」没有日子时这一项不适用。
- 「星期」的对照用窗口内铺开前不过节的周一、三、四（不是窗口外）；节日、日期的「平常工作日」优先用窗口外的，窗口外没有时用窗口内的，并在文字里写明用的是哪段；都没有时不写倍数。
- 写死的时间文案改为由数据填写：「2025 年 8 月」、「8/22 起全国做克减」等标题，以及 `context.ts` 里问答上下文的「2025 年 8 月全国」。
- `InsightGraph.scope` 增加 `range: { from, to } | null`、`dataFrom`、`dataTo`、`festivals: Array<{ name, from, to }>`、`overlap: string | null`（窗口里有落在克减铺开日之后的节日日时给出说明文字，否则为 null）。

## 6. 页面

- 时间控件见第 3 节。切换范围即重新请求，期间保留旧图并显示加载提示；首次计算一个新范围预计约 1 分钟（全表扫描，具体取决于交易日期索引）。
- 非全月时顶部常驻一行：范围、店数，以及 `overlap` 说明（例：「七夕 8/23–8/29 · 5,612 家店 · 七夕与全国克减重叠，节日效应和活动效应分不开」）。
- 不适用的节点、连线置灰，点开显示原因。

## 7. 错误处理

- 范围不合格：400 + 原因，页面在控件旁提示，图保持上一次的范围。
- 查询超时或失败：沿用现有错误展示，提示可重试；失败的范围不进缓存。
- 门店不够做门店间比较的情况不单独处理：真实数据每天 5,000 多家店有成交，3 天以上的范围不会出现。测试里用几个短范围确认图上所有数字都是有限值（没有 NaN、Infinity）。

## 8. 测试

用 `tests/helpers/insight-fixture.ts` 的合成数据，不连库：

- 7 天窗口时门店门槛为 5 天，门店列有结果；全月门槛仍为 20 天，全月图数字不变（快照对比现有测试）。
- 「七夕」「星期」「新增还是挪动」三处不适用的判定和不判定各一例。
- 平日对照组只取窗口外、铺开日前的周一、三、四。
- 范围校验：格式错误、倒序、越界、短于 3 天各被拒绝。
- 内存缓存按范围分开，同范围并发只计算一次。
- 最后起服务看七夕范围的真实图并截图确认。

## 9. 未核实

- 本地表是否有交易日期索引，决定首次计算耗时。
- 7 天数据下同类店对比每组样本是否够；不够的组按现有规则并组或不比，图上结论会变少。
