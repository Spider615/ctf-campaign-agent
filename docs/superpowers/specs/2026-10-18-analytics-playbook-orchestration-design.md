# 营销分析编排重构：分析计划即程序

日期：2026-10-18。状态：待用户确认。前置：`2026-10-18-analytics-semantic-layer-design.md`（已实现，对账 56/56 一致）。

本文替换 `2026-10-13-general-analytics-agent-design.md` 的编排、答案与复核部分。只读、数字只认代码计算、证据可展开、可取消、1811 执行隔离这些约束不变。

## 1. 问题

语义层上线后，用真实模型并发重跑 S1–S5：首稿 1–8 分钟就能出来，但首稿之后还要 10–16 分钟。第一轮复核几乎都会退回；被拒最多的工具调用仍是「计算引用必须属于相同范围」。答案冗长没有重点，图表与结论脱节。

上一版草稿用「按问题类型写固定路径、保留旧流程兜底、复核改成不阻断、加墙钟上限」来解决。这些办法都是在现有结构外面加规则，原因没有消除，所以弃用。

## 2. 根因

拆到机制层面，有四个原因：

1. 计划是隐式的。模型通过几十次增量工具调用，边试边决定要比什么。每次调用单独校验，错一次就退回一次，所以总耗时取决于试错次数，没有上界。
2. 计算是自由的。`calculate_analysis` 允许拿任意事实做四则运算，于是跨范围拼数成了模型的默认做法，再由校验规则一条条挡回去。
3. 答案是自由文本。数字、方向、口径写在正文里，只能靠事后复核逐句核对。复核每轮整篇重读、要求零问题，每轮又往正文里补说明，于是答案越写越长，每轮都有新问题。
4. 图表与结论没有结构关联。图只能引用某一次查询的原始结果，真正支撑结论的、经过加工的比较画不出来，能画的又往往不是结论需要的。

这四个原因都是同一件事：分析的结构没有被表达出来，只存在于模型的多轮对话和正文里，代码看不到，只能在外面拦。

## 3. 设计

把分析的结构做成一等公民，用一份声明式的分析计划表达。代码对计划做静态校验，一次执行完，再从证据生成答案骨架。模型只做两件事：写计划，写结论措辞。

```text
问题 → 计划（模型）→ 静态校验（代码）→ 执行（代码，并行）→ 结论（模型）→ 绑定与渲染（代码）→ 答案
                ↑ 不通过：一次性返回全部问题，模型改一次
```

### 3.1 分析计划

计划是一组节点组成的有向图，每个节点是语义层上的一个算子：

| 算子 | 作用 | 产出 |
|---|---|---|
| `measure` | 范围 × 指标 × 可选分组 | 各组指标值 |
| `contrast` | 目标范围对参照范围，可声明对齐方式（共同门店、同日、控制层） | 目标、参照、差额、相对变化 |
| `decompose` | 拆解一个 contrast：数量、单价、结构 | 各部分的贡献 |
| `drill` | 沿语义层的层级路径下钻一个 contrast 或 measure | 每层偏离及其样本量 |
| `scan` | 在语义层可扫描的维度上展开一个 contrast 或 measure | 偏离排序及其样本量 |
| `robust` | 对另一个节点做稳健性检查：剔最大门店、剔最大单、替代窗口、半段稳定性 | 结论方向是否保持 |
| `scenario` | 在一个 measure 上套用假设规则 | 条件测算 |

范围直接用语义层的表达方式：时间写日期、节庆或活动期次；筛选写语义维度的取值；口径写销售、净额、退货或回收。指标只能是语义层登记过的指标。

这样，「七夕日均和其他日子比」是一个 contrast；「两档克减在四种口径下比」是四个对齐方式不同的 contrast；「找新角度」是一个 scan 加上 robust。不需要为问题类型写分支，问题的差别全部体现在计划里。

自由四则运算被删除。原来需要它的场景，都由算子或语义层指标表达：跨范围比较用 contrast，比率用语义层指标，保本用 scenario。

### 3.2 静态校验

计划执行前，代码一次性检查全部节点：

- 每个指标、维度、筛选取值是否存在于能力目录；
- 指标要求的控制维度是否满足，例如每克指标需要同货类、同材料；
- 指标的口径要求是否满足，例如单均只适用于销售口径；
- 范围是否在数据覆盖和用户硬范围之内；
- 节点之间的引用是否成立，例如 decompose 必须指向一个 contrast。

全部问题一次返回，模型改一次计划。第二次仍不通过，就丢弃不通过的节点，其余照常执行，未执行的节点在答案中注明。整个过程中，模型最多写两次计划。

### 3.3 执行

代码按依赖关系并行执行计划，结果写入现有证据注册表（事实、对象、方法检查保持原合同）。模型看完执行结果后，可以追加一次补充计划，例如发现某个分区异常后再下钻一层。补充计划只能有一次，同样要经过 3.2 的静态校验。

### 3.4 结论与答案

模型不写数字，只写结论，每条结论都绑定到计划里的一个节点：

```ts
type Claim = {
  node: string;                                   // 计划节点 id
  select?: Record<string, string>;                // 节点结果中的哪一组，例如 { district: "南区/B区" }
  metric: string;
  assert: "up" | "down" | "flat" | "higher" | "lower" | "largest" | "smallest" | "unavailable";
  text: string;                                   // 措辞模板，数字位置写 {value}、{delta}、{change}、{target}、{reference}
};
type Answer = { headline: Claim; claims: Claim[]; actions: Array<{ text: string; claim: number }>; questions: string[] };
```

代码负责：

- 绑定：按 node、select、metric 取出事实，把数字填进模板。取不到的结论直接丢弃。
- 方向校验：`assert` 必须与事实的正负或排序一致，不一致的结论丢弃。
- 可信度：从指向同一节点的 robust 结果计算，取值为方向保持、方向翻转或未检查。可信度在结论旁展示，模型无法修改。
- 限制说明：从本次用到的语义定义自动生成。依据为推断的项归入「口径待确认」，按定义去重。
- 不能下的结论：从三处自动汇总：能力目录缺少的维度、结果为 `unavailable` 的结论、方向翻转的稳健性检查。模型可以补充，但不能删除。

结构上的上限：headline 1 条，claims 最多 5 条，actions 最多 3 条。上限写在 schema 里，不靠提示词约束。

数字、方向和口径都由代码保证，模型写的只有措辞。数字错、方向反、口径漏这三类问题因此不会发生，复核也不再需要检查它们。

### 3.5 复核

复核检查的是剩下两类只有语义判断才能发现的问题：计划有没有回答原问题，措辞有没有超出所绑定证据的含义（例如把相关写成因果）。

- 计划复核：在执行前对计划做一次（计划很短，耗时是秒级）。不通过时，与静态校验的问题合并，让模型改那一次计划。
- 措辞复核：对结论列表做一次，结果用「改写」或「删除」作用到具体结论上，不再整篇重写。

两次复核各最多一轮，所以总的模型调用次数由结构决定：计划最多 2 次、补充计划最多 1 次、结论 1 次、复核 2 次，一共不超过 6 次。这不是另外加的上限，而是流程本身就只有这么多步。

### 3.6 图表

图从证据的形状推出，不让模型挑选：

- headline 绑定的节点是带分组的 drill 或 scan：画偏离排序条形图，只画样本量达标的组；
- 绑定的是多个对齐方式不同的 contrast：画分层对比图；
- 绑定的是按日期分组的 measure：画折线图；
- 其他情况不出图。

图的数据来自节点结果，可以跨节点组合。整篇最多 1 张图，跟着 headline 走。

## 4. 替换范围

| 现在 | 处理 |
|---|---|
| `agent/general-analytics-run-turn.ts` 多窗口循环、起草窗口、修订窗口 | 删除，改为计划 → 执行 → 结论的固定流程 |
| `analyze_history`、`calculate_analysis`、`simulate_analysis`、`read_analysis_state` 等增量工具 | 删除，换成 `submit_plan`、`submit_followup`、`submit_claims` 三个工具 |
| `AnalysisDraft`（blocks、conclusions、coverage） | 删除，换成第 3.4 节的 `Answer` |
| 草稿校验、语义复核的整篇模式、复核缓存 | 删除，换成绑定校验和两段复核 |
| 图表放置（`present_analysis_chart`） | 删除，图由代码从 headline 推出 |
| 分析操作 `createAnalysisOperations` 的五种方法 | 保留计算内核，改为由计划节点调用；方法参数改为节点 schema |
| 证据注册表、数据库适配器、语义层 | 保留 |
| `analytics-run-turn.ts`（导入报告的旧问答） | 不在本次范围；它服务的是导入报告模式，不走数据库分析 |
| 页面上的答案组件 | 按新 `Answer` 重写。会话只存在浏览器 sessionStorage，旧格式答案按纯文本展示，不再维护旧渲染 |

不保留旧流程兜底。计划表达不了的问题（例如需要用到语义层还没有的数据），答案就明确说明缺什么。

## 5. 验收

- 合成数据：每种算子的计算正确；静态校验能拦住每一类错误；绑定、方向校验和可信度计算正确；图表推导规则正确。
- 假模型：给定计划和结论，覆盖完整流程，包括计划修改、补充计划、结论丢弃和复核改写。
- 真实模型跑 S1–S5：记录每题的模型调用次数（应 ≤ 6）和耗时；答案里的数字逐个与对账脚本比对；S4、S5 必须明确说出缺少会员等级和金价，并给出现有数据能回答的最接近问题。

## 6. 需要你确认

1. 删除自由四则运算和增量工具。模型只能在算子范围内分析，算子不支持的分析方式要先扩展算子才能用。
2. 不保留旧流程兜底，旧格式的答案只按纯文本展示。
3. 补充计划限定一次。如果业务上常需要多轮追问式分析，应当作为用户的下一轮对话，而不是放在同一轮里。
