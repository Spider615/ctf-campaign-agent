# 浅色 AI 工作台与真实工具轨迹设计

> 本文补充 `2026-09-16-ics1811-sop-agent-design.md`，只调整界面、Agent 工具边界与过程事件传输。ICS-1811 字段规则、两轮追问上限、原话守卫、确认条件和最终填写值仍以原设计为准。

## 1. 目标与边界

### 1.1 目标

1. 把当前米白、深酒红界面升级为浅冰蓝科技工作台，让客户第一眼感到这是一个真正执行任务的 AI Agent，而不是普通表单聊天框。
2. 在 Agent 工作期间流式展示真实工具调用，包括字段提取、代码表查询、规则分析、文案生成、复述和填写值生成。
3. 工具由 Agent 发起或由 Agent 编排器强制调用，工具内部继续运行确定性业务代码；模型不能改写代码表、校验结果或追问目录。
4. 保留对话为主、1811 草稿为辅的产品结构，并在桌面、平板和手机上保持可用。
5. 已完成的工具轨迹进入消息记录，默认折叠成简洁摘要，可以展开审计。

### 1.2 不做

- 不展示或伪造模型隐藏思维链，只展示工具名称、公开动作、耗时和安全的结果摘要。
- 不连接真实 ICS-1811/1815/1816，不改变现有 demo 数据边界。
- 不改变 SOP 业务规则，不放宽用户原话、数值、代码表和确认守卫。
- 不引入新的动画库或大型 UI 依赖；使用现有 React、Tailwind、Lucide 和 CSS 动画。
- 不为了视觉统一重写 `components/ui/` 原始组件。

## 2. 视觉系统

### 2.1 方向

整体采用“浅色 AI 工作台”：大面积白色和冰蓝背景、少量高饱和电光蓝、半透明卡片、细描边和柔和光晕。酒红与金色退为周大福品牌标识和极少量强调色，不再占据整块侧栏。

建议的全局语义色：

| Token | 建议值 | 用途 |
|---|---:|---|
| `--background` | `#EEF6FF` | 页面冰蓝底色 |
| `--surface` | `rgba(255,255,255,.88)` | 主面板和侧栏 |
| `--surface-blue` | `#F2F7FF` | 工具轨迹和辅助区 |
| `--primary` | `#247CFF` | 主按钮、当前步骤、执行中状态 |
| `--primary-soft` | `#DCEBFF` | 选中态、浅色标签 |
| `--foreground` | `#17243A` | 主文字 |
| `--muted-foreground` | `#8295AE` | 次要说明 |
| `--border` | `#D9E7F6` | 默认边框 |
| `--success` | `#20A674` | 完成、在线 |
| `--warning` | `#D9862A` | 待确认、非阻断提醒 |
| `--brand-ruby` | `#8C2038` | 品牌徽标、少量品牌提示 |
| `--brand-gold` | `#C99A4B` | 品牌辅助色 |

视觉比例约为 80% 白色/冰蓝、15% 淡蓝容器、5% 电光蓝和品牌色。页面背景使用低透明度网格与径向光晕，不能影响文字对比度。

### 2.2 排版、圆角与阴影

- 沿用系统中文字体栈，标题使用 600–700 字重，正文至少 14px；工具代码名使用等宽字体。
- 主容器圆角 20–22px，卡片 14–18px，输入框 18px，标签使用胶囊形。
- 阴影以蓝灰色低透明度为主，不使用黑色重阴影。
- SVG/Lucide 图标承担功能提示，不使用 emoji 作为功能图标。

### 2.3 动效

- 工具执行中使用呼吸光点、三点加载和轻微描边光晕。
- 新工具步骤淡入并上移 4–6px；完成状态在 180–240ms 内切换。
- 不做持续移动的大背景、不做 3D 翻转、不动画布局宽高。
- `prefers-reduced-motion` 下关闭循环动画，保留静态状态差异。

## 3. 页面结构

### 3.1 桌面端（≥1280px）

页面采用三栏工作台：

1. **左侧 252px**：品牌、蓝色“新建优惠活动”按钮、最近活动列表和 Agent 在线状态。当前活动使用浅蓝底、蓝色左边线和轻微光晕。
2. **中间主区**：活动标题、五步进度条、对话消息、流式工具卡和固定在底部的输入框。对话仍是视觉主体。
3. **右侧 350–420px**：实时 1811 草稿，显示完整度、填写值、待确认、校验和版本。当前轮新增字段使用浅蓝高亮。

右侧面板继续支持收起与拖拽宽度。用户主动收起后，中间对话区占满剩余空间；“查看填写值”重新展开面板。

### 3.2 平板与手机

- 768–1279px：隐藏固定右栏，通过右侧抽屉查看填写值；左侧栏可缩窄或折叠。
- <768px：左侧导航改为抽屉，只保留单列对话；工具卡铺满消息宽度；进度条横向滚动。
- 所有可点击控件至少 44×44px；无横向页面滚动。

### 3.3 首页

- 保留“一句话开始”和玩法模板，但改为浅色玻璃工作台首页。
- 首屏标题更紧凑，输入框成为视觉中心，带蓝色聚焦光晕。
- 在输入框下方展示“8 个工具已连接 · ICS 规则库 · 代码表 · 版本记录”，提前建立 Agent 心智。
- “看一个完整示例”继续存在，使用次级按钮样式。

## 4. 真实工具模型

### 4.1 原则

规则引擎也作为 Agent 工具暴露。模型或 Agent 编排器只负责发起调用；工具内部调用现有纯函数并返回确定结果。Workers 在提交消息和版本前再次执行现有 `deriveFill → checkDraft → planNext` 流程，最终状态永远以服务端复核为准。

不得为了让轨迹更热闹拆成大量无意义小工具。一个工具应代表用户能理解的一段业务能力。

### 4.2 工具目录

| 工具 | 调度方式 | 内部能力 | UI 描述 |
|---|---|---|---|
| `extract_campaign_facts` | 模型调用 | 现有 `update_fields` + `applyFactWrites` | 提取活动信息并核验用户原话 |
| `lookup_ics_reference` | 模型调用、只读 | 查询 `codebook.ts` 的门店、区域、货类、优惠类型及来源 | 查询 ICS 代码表 |
| `analyze_campaign_state` | 模型调用；结束前强制存在 | `deriveFill`、`gapsOf`、`checkDraft`、`planNext` | 匹配 1811 字段并运行业务规则 |
| `draft_campaign_copy` | 模型调用 | 现有 `draft_copy` 守卫 | 起草活动名称和门店说明 |
| `build_campaign_readback` | 模型调用；满足条件时强制存在 | `buildReadback`，结果只作为预览，Workers 重新生成最终版本 | 生成白话复述 |
| `generate_ics1811_sheet` | 确认后由 Agent 编排器调用 | `renderFillSheet`；未确认、旧版本或有阻断时拒绝 | 生成 1811 逐项填写值 |
| `confirm_campaign_readback` | 用户打字确认时由模型调用 | 现有 `confirm_readback` 守卫 | 核对用户是否确认最新复述 |
| `undo_campaign_change` | 模型调用 | 现有 `undo_last_change` | 撤销上一轮修改 |

点击确认按钮、卡片提交和面板编辑不需要为了“像 AI”而额外调用模型；它们由 Agent 编排器直接调用同一工具目录并产生真实轨迹。这样既保留工具化展示，也避免不必要的模型延迟和成本。

### 4.3 强制复核

- Agent 回合结束前，服务端检查本轮所需工具是否已调用。首句或普通文本修改至少需要 `extract_campaign_facts`（若没有可写事实可以返回“未识别到修改”）和 `analyze_campaign_state`。
- 用户只询问字段含义或操作方法、没有要求修改活动时，可以直接回答，不强制调用写工具，也不制造空轨迹。
- 需要名称或内容时必须调用 `draft_campaign_copy`；进入复述时必须调用 `build_campaign_readback`。
- 工具漏调时，Agent 服务允许一次补调；仍漏调则由编排器执行确定性工具并在轨迹中标记“系统补跑”。
- Workers 仍按现有逻辑重算填写模型、校验和下一步，Agent 返回的复述与填写值不能直接落库。

## 5. 工具事件与数据流

### 5.1 事件协议

新增共享类型 `AgentTraceEvent`：

```ts
type AgentTraceEvent = {
  id: string;
  tool: AgentToolName;
  title: string;
  status: "started" | "completed" | "warning" | "failed";
  summary?: string;
  durationMs?: number;
  initiatedBy: "model" | "orchestrator";
};
```

`summary` 只能包含数量、公开字段名称、校验数量和用户已在对话中提供的非敏感摘要，不转发完整工具入参、系统提示词、模型思维或内部堆栈。

### 5.2 流式链路

1. 客户端提交 `interpret`、`text` 或 `confirm` 回合。
2. Workers 的 turn route 立即返回 NDJSON 流，先发 `run_started`，保证页面立刻出现执行卡。
3. Workers 调用 Agent 服务的流式 `/turn/stream`；Agent 服务在工具 handler 开始和结束时发 `tool_started` / `tool_finished`。
4. Workers 转发安全事件，并在 Agent 完成后执行现有业务复核、版本提交和消息落库。
5. Workers 发终态 `snapshot`；客户端用正式 Snapshot 替换乐观 UI。
6. 完整轨迹以 `agent_tool_trace` 消息保存，重新打开会话时仍可展开查看。

原 `/turn` JSON 接口保留为测试和兼容入口；浏览器 UI 使用流式入口。`card`、`edit`、`dismiss`、`undo`、`rollback` 等快速确定性操作可以沿用 JSON 响应，但调用统一工具目录时也写入对应轨迹。

### 5.3 消息结构

新增：

```ts
type ToolTrace = {
  status: "completed" | "warning" | "failed";
  durationMs: number;
  steps: AgentTraceEvent[];
};

type StoredMessage =
  | ExistingMessages
  | { v: 2; kind: "agent_tool_trace"; trace: ToolTrace };
```

流式执行时使用内存中的临时 trace；提交完成后以服务端保存的 `agent_tool_trace` 为准。`messageToText` 只输出“AI 完成 N 个工具步骤”，避免把冗长轨迹塞回后续模型历史。

## 6. 组件设计

### 6.1 新组件

- `chat/tool-run-card.tsx`：执行中与历史轨迹的共同容器。
- `chat/tool-step.tsx`：单个工具步骤，负责状态图标、工具代码名、摘要和耗时。
- `chat/agent-avatar.tsx`：浅蓝科技感 Agent 标识与在线点。
- `app/lib/client/stream.ts`：NDJSON 解码和终态 Snapshot 提取，保持 UI 组件不关心协议细节。

### 6.2 现有组件调整

- `app-shell.tsx`：浅色侧栏、品牌区、会话选中态和 Agent 在线卡。
- `empty-state.tsx`：浅色工作台首页、主输入框和工具连接提示。
- `conversation.tsx`：接收流式事件，维护临时 trace，并在终态切换到 Snapshot。
- `message-view.tsx`：渲染持久化工具轨迹；完成后默认折叠。
- `thinking-indicator.tsx`：由 `ToolRunCard` 取代，不再只显示三个跳动圆点。
- `draft-panel.tsx` 与 `fill-sheet-view.tsx`：浅色面板、完整度与本轮新增字段高亮。
- `globals.css`：集中定义新的语义 token、背景和动效，业务组件不散落硬编码色值。

## 7. 工具卡交互

### 7.1 执行中

- 标题为“AI 正在搭建活动”，显示呼吸光点和总耗时。
- 当前步骤展开并显示动态状态；完成步骤显示结果摘要和耗时；等待步骤降低对比度。
- 每个工具显示中文名称和较小的代码名，例如“查询 ICS 代码表 `lookup_ics_reference`”。
- 新事件到来后只滚动到当前卡片，不反复抢夺用户滚动位置。

### 7.2 完成后

- 自动折叠为“完成 5 个工具步骤 · 3.8 秒”，保留成功、提醒或失败颜色。
- 点击可展开完整步骤；复制消息时只复制摘要。
- 若某步由编排器补跑，详情中显示“系统补跑”，不冒充模型调用。

### 7.3 失败与重试

- 工具拒绝业务输入时使用 warning，不把整个回合渲染成系统故障。例如原话证据不足时显示“1 项未写入，等待补充”。
- Agent 服务、网络或超时失败时当前步骤变为 failed，并保留现有重试入口。
- 流中断但服务端可能已提交时，客户端先重新拉 Snapshot；只有确认未提交才允许重试，避免重复版本。
- 工具内部异常只向用户显示友好摘要，详细错误留在服务端日志。

## 8. 可访问性与性能

- 正文与背景对比度至少 4.5:1；状态不能只依赖颜色，同时使用图标和文字。
- 工具卡使用 `role="status"`，只播报当前步骤变化；历史详情不使用持续 `aria-live`。
- 所有图标按钮有可见或无障碍名称，保留键盘焦点环。
- 避免长列表动画和布局抖动；执行卡预留合理最小高度。
- 流事件按 `id` 合并，同一工具频繁更新时批量到一帧渲染。

## 9. 测试与验收

### 9.1 自动测试

1. 工具单测：每个工具的成功、拒绝和守卫路径；规则工具结果与直接调用现有纯函数一致。
2. 协议单测：NDJSON 分片、半行、错误行、终态 Snapshot 和连接中断。
3. 回合集成测试：真实工具事件顺序、漏调补跑、失败持久化、最终服务端复核。
4. 消息单测：`agent_tool_trace` 编解码、`messageToText`、旧会话兼容。
5. 前端测试：执行中、完成、warning、failed、折叠和 reduced-motion 状态。
6. 保持现有 `npm test`、页面与 Agent TypeScript、lint、build 全部通过。

### 9.2 视觉验收

- 1440×900：三栏同时可见，工具卡是对话主视觉，右侧草稿不挤压主消息阅读。
- 1024×768：右侧改抽屉，工具卡完整，无横向滚动。
- 390×844：单列可用，输入框不被软键盘遮挡，所有按钮满足触控尺寸。
- 执行首个状态在提交后立即出现；真实工具开始、完成、失败状态与服务端事件一致。
- 页面不出现大面积深色背景；电光蓝只用于当前动作和重点信息。

## 10. 完成标准

1. 首页、侧栏、对话、工具卡、填写值面板和移动端完成浅色科技风统一改造。
2. 所有展示的已完成工具步骤都对应真实执行；没有假进度、假调用或思维链文本。
3. 规则能力以 Agent 工具形式提供，但现有确定性代码仍是最终裁决者。
4. 工具轨迹实时显示、完成后落库并可审计，失败可安全重试。
5. 现有 ICS-1811 业务验收标准不回退，全量验证命令通过。
